# proj035 — ボードの送り出しが ≒ 230 Mbit/s で頭打ちになる原因を切り分け、除けるなら除く

日付: 2026-10-28（起こし）
土台: PL は変えない。仕様は YATSUGATAKE 975cbbf（interface 8. の 12、予算は 1 ボード 20 MB/s に決めた）
状態: **完了**（2026-10-28。GEM1 の AXI_MAX_PIPELINE を 0x0101 → **0x0102**（読みの要求 2 本）にして送り出し 194 → 348 Mbit/s。2G-4 の運用の形で 30 分の照合を通過。起動時のユニットで書く）

着手の前に [`../LESSONS.md`](../LESSONS.md) を全部読む（知見の全部は [`../docs/lessons_all.md`](../docs/lessons_all.md)）。

## 目的

ボード → PC の送り出しが TCP 1 本 25.3 MB/s・UDP 231 Mbit/s（損失 0 %）で頭打ちになる（proj021 の M-1。普通の GbE なら ≒ 940 Mbit/s）。
**原因をボードの中 / 外、PS の設定 / ドライバ / 経路のどれかまで切り分け、除けるなら除く**。予算（20 MB/s）は頭打ちのままでも入るが、使用率 79 % で追いつきの余裕が薄い（2026-10-28、開発者「原因が分かって取り除けるなら、そのほうが好ましい」。2G の移植より先に）。

## 仮説（予言は走らせる前に。どれが当たるかを先に書く）

| | 仮説 | 当たりなら見えること |
|---|---|---|
| H1 | **PS のクロックの設定**（GEM の参照・IOU / LPD の AXI のクロック）が、Overlay の読み込み（PS のプリセット）で下がっている | Overlay を載せる前（起動直後）は速く、載せた後に 230 Mbit/s に落ちる。`clk_summary` の gem・lpd の値が変わる |
| H2 | **経路（スイッチ・ポート・宛先の PC）** | ボード ↔ PC の直結で速くなる。UDP の損失 0 % と合わないので見込みは低い |
| H3 | **ドライバ（macb）の割り込みの扱い**（フレームごとに 1 回・CPU0 だけ・まとめない）で 1 フレーム ≒ 50 µs かかる | フレームの大きさに依らずフレームの数で頭打ち（`-l 200` で Mbit/s が ≒ 1/7 に落ち、フレーム / s は同じ）。割り込みを別の CPU に移すと動く |
| H4 | **CPU の周波数**（cpufreq が低い側に張り付く） | `cpufreq` の今の値が最大より低い。performance に替えると速くなる |

**予言（2026-10-28）**: 最も見込みが高いのは **H1**（受ける向きも半分以下で、CPU は空き、損失 0 % ＝ NIC 自身が遅い。ドライバの割り込みの重さだけなら CPU が埋まるはず）。次が H3。H2・H4 は低い。

## 手順（配線を変えない順。1 回のボードの会話で T-0〜T-4、直結 T-5 は配線を変えるので最後）

各手順は 予言 → 結果 → 当たり・外れ → コミット。測った条件（宛先・スイッチ・ケーブル・Overlay の有無・時刻）を毎回書く。

- **T-0 環境**: `uname -a`・`ethtool eth0`・`ethtool -i eth0`・`ethtool -k eth0`・`cat /proc/interrupts | grep eth`・`cpufreq` の今の値と上限・`/sys/kernel/debug/clk/clk_summary` の gem・lpd・iou の行（debugfs が要る）・`dmesg | grep -i macb`
- **T-1 起動直後（Overlay を載せない）**で iperf3 TCP 30 s × 3・UDP 900 Mbit/s × 1（proj021 と同じ宛先）
- **T-2 Overlay を載せた後**（proj031 rev 2 の .bit。2G の運用の形）で T-0 の clk の行と T-1 を繰り返す。**T-1 と T-2 を交互に 2 回**（ボードを起動し直して）
- **T-3 `-l 200` の UDP**（H3: フレームの数か量か）
- **T-4 割り込みを CPU1 に**（`/proc/irq/<n>/smp_affinity`）・cpufreq を performance に（H3・H4）
- **T-5 直結**（ボード ↔ PC、別の NIC）で T-1（H2）
- 当たった仮説に応じて直し方を決める（H1 なら PS のプリセットの GEM・LPD のクロックを YATSUGATAKE の build.tcl で明示する、など。RTL は変えない）

|---|---|---|---|---|---|

- **フレームの数でも量でも頭打ちでない**: 1 フレームの時間 ≒ 16.4 µs ＋ 25 ns × バイト（3 点で ±1 µs に乗る）。25 ns / バイト ≒ 40 MB/s は 1 GbE の線（8 ns / バイト）より 3 倍遅い → 線ではなく、ボードの中でバイトに比例して時間を食う所がある（DMA の読み・キャッシュの掃除・コピー）。予言の H3（フレームごとの割り込みだけ）は**外れ**（それならフレーム / s が一定）
- UDP 900M の 10 s の間の CPU（/proc/stat）: **CPU0 sys 57 %・softirq 12 %・idle 27 %**、CPU1 sys 12 %、CPU2・3 は空き。全体では 83 % 空きに見えるが、CPU0 は 7 割埋まっている（proj021 の「96.8 % 空き」は 4 コアの平均で、CPU0 の偏りを見ていなかった）。埋まり切ってはいないので CPU0 だけでは説明できない

### 原因: GEM の AXI の出しっぱなしの要求が 1 本（AXI_MAX_PIPELINE = 0x0101）

GEM1 のレジスタ（/dev/mem）: DMACFG 0x70180f10（INCR16・TX パケットバッファ 4 KB・RX 最大・チェックサムの肩代わり on・64 bit の番地）、NCFGR は 64 bit のバス・GBE・全二重・PAUSE を受けない。**AXI_MAX_PIPELINE（0x054）が 0x0101 = 読み 1・書き 1**。
読みの要求が 1 本だと、128 B のバースト 1 回に ≒ 4.5 µs かかっている計算（28 MB/s ÷ 128 B）で、T-3 の「1 フレーム 16.4 µs ＋ 25 ns × バイト」とも、RX（書き）も 415 Mbit/s で止まることとも合う。

**動いているまま 0x054 を書き換えた**（ssh が eth0 を通るので、PC に 40 s 届かなければ再起動する見張りを先に起こした）:

| AXI_MAX_PIPELINE | UDP（`-l 1400`） | TCP 1 本 | PC → ボード（`-R`） |
|---|---|---|---|
| 0x0101（既定） | 227 | 194〜203 | 415（再送 3,844） |
| **0x0808** | **442**（損失 0） | **425**（再送 0） | 461（再送 3,922） |
| 0x1010 | 408 | 424 | 460 |
| 0x2020 | — | — | — （**書いた直後に GEM が止まり、見張りが再起動した**） |

- **0x0808 で TCP が 2.2 倍**（194 → 424 Mbit/s = 53 MB/s）。**5 分の連続（TCP 300 s）で 424 Mbit/s のまま 5 区間とも同じ・再送 0・誤り 0**
- 8 と 16 で変わらないので、**もう 1 つ天井がある**（≒ 425〜440 Mbit/s）。要求 1 本あたり 4.5 µs という読みの遅れそのものが異常に長い（DDR の読みの遅れは普通 1 µs を大きく下回る）。LPD → DDR の道の遅れを ADMA（dmatest）で測ろうとしたが、組み込みの dmatest が 1 回しか回らず値が取れなかった（未）
- 0x2020 で止まった理由は確かめていない（上限が 16 の見込み）。**0x0808 より大きくしない**

### 起動のたびに 0x0808 を書く（2026-10-28 02:00、開発者の了解）

- `board/gem-axi-pipeline.py`（/dev/mem で 0x0808 を書き、読み返して違えば 1 で終わる）と `board/gem-axi-pipeline.service`（oneshot、network-pre.target の前）をボードに入れ、起動し直して「0x0101 -> 0x0808」・active (exited) を確かめた。リンクの down / up では 0x0808 のまま（戻らない）。手順は `proj001/docs/runbook.md` の 09

- **交互に並べた**（180 s ずつ、同じ形、同じ日）:

|---|---|---|---|---|

- 読み: 0x0101 でも 1 周の最長 30 ms と 3 BASE（30.72 ms）にほぼ余裕が無い（tint 30.72 ms はリングの読みと束ねが Python の道。proj029 の C の道は n_sum 1 だけ）。0x0808 で何かがこの道を遅くし、追いつけなくなる。**何が遅くするかは確かめていない**（GEM の要求 8 本と CPU のメモリの読みの取り合い・割り込みの増え方が候補）
- 起動時のユニットは **disabled に戻し、レジスタも 0x0101 に戻した**（ファイルはボードに残してある。`systemctl enable` で戻る）

### L-1・L-2 何が取得を遅くするか（2026-10-28 03:00〜04:40）

**バイトの意味を取り違えていた**: AXI_MAX_PIPELINE の**下の byte が読み**（送信で GEM が DDR から読む）、**上の byte が書き**（受信で DDR に書く）。0x0801 は送り出し 194 のまま・PC → ボード 415 → 458、0x0108 は送り出し 420。上の T 段の表の「読み・書き」は、この意味に読み替える（0x0808 は両方 8 本なので結果は変わらない）

送り出しと読みの要求の本数（TCP 15 s）: 1 本 194・**2 本 350**・4 本 403・8 本 420 Mbit/s

**L-1 取得の 1 周の内訳**（specd を毎回起こし直し `--loop-log-ms 0.1`、同じ形 = 2G-4・ネットワークの tint 30.72 ms・この PC へ ≒ 16 MB/s、60 s ずつ交互。`../proj031/tools/loopsum.py`、値は出口の記録 1 本 = 30.72 ms あたり）

| 設定 | リングの読み | 振り分け | 窓の記録 | 計 | miss・照合 |
|---|---|---|---|---|---|
| 0x0101（2 回） | 11.6・11.7 | 4.3・4.2 | 8.2・8.1 | 26.3・26.2 | 0・通過 |
| 0x0808（2 回） | 11.7・11.8 | 4.4・4.4 | **15.0・15.0** | **31.6・31.7** | 360〜370・失敗 |
| 0x0801（書き 8・2 回） | 11.6・11.7 | 4.2・4.2 | 8.0・8.1 | 26.1・26.2 | 0・通過 |
| 0x0108（読み 8・2 回） | 11.7・11.8 | 4.3・4.4 | **15.1・14.9** | **31.6・31.6** | 340〜390・失敗 |
| 0x0102（読み 2・2 回） | 11.6・11.7 | 4.3・4.2 | 8.2・8.2 | 26.3・26.3 | 0・通過 |
| 0x0104（読み 4・2 回） | 11.7・11.6 | 4.2・4.2 | **14.0・14.0** | **30.5・30.5** | 0（loop_slow 216）・通過、すれすれ |

- 伸びるのは「窓の記録」（束ね・C の記録・溜まりへの put）だけで、どれも ≒ 2 倍。遅れが溜まる前の周 2 から遅い（遅れの結果ではない）。DDR から PL の書いたものを読む「リングの読み」は変わらない
- 効くのは**読みの要求**（送信の側）。2 本までは無害で、4 本でほぼ効ききる（段のように悪くなる）

**L-2 CPU から見た DDR**（`board/membench.c`、CPU3 に固定、ポインタの追いかけ 64 MiB・memcpy 4 MiB、8 s、2 巡で ±1 %。iperf3 は CPU1）

| 設定 | 送るもの | 読みの遅れ | memcpy |
|---|---|---|---|
| 0x0101 | なし / 130 Mbit/s | 147 / 151 ns | 2.44 / 2.30 GB/s |
| 0x0102 | なし / 130 Mbit/s | 147 / 153 ns | 2.44 / 2.30 GB/s |
| 0x0108 | なし / 130 Mbit/s / 制限なし | 147 / **190** / **586** ns | 2.44 / **1.77** / **0.57** GB/s |

- **GEM が読みの要求を 8 本出すと、16 MB/s しか送っていなくても CPU の DDR の読みの遅れが 3 割増え、写しが 3 割落ちる**。これが取得の写しの多い段（束ね・記録・put）を遅くした。16 MB/s は DDR の帯域の 1 % に満たないので、量ではなく、GEM の深い読みが DDR までの道（LPD の側）で CPU の読みを待たせていると見る。GEM の要求 1 本の遅れが ≒ 4.5 µs と長いことと同じ根の見込み（確かめていない）
- 0x0101 と 0x0102 の「制限なし」は、前の iperf3 が受けをふさいで送れていなかったので外した

### 0x0102 で 30 分（2026-10-28 04:06〜04:36、運用の形 = 2G-4・ネットワークの tint 30.72 ms・この PC へ）: 通過

- miss 0・kgap 0・pl_drop 0・pl_crc 0・pl_err 0・loop_slow 1・1 周の最長 30.8 ms・リングの山 4.7 MB、30 分を通して 0x0102 のまま
- 受け: 29.8 GB（16.6 MB/s）・CRC 0・欠け 0・照合 通過
- 起動時のユニットを 0x0102 で入れ直して有効に（起動し直して「0x0101 -> 0x0102」、送り出し TCP 348 Mbit/s）

## 結論・次にやること（2026-10-28）

- **頭打ちの主因は GEM1 の AXI_MAX_PIPELINE の読みの要求が 1 本（0x0101）**。予言の H1〜H4 は全部外れ。PYNQ の掲示板にも RFSoC4x2 の同じ症状（原因は未特定）
- **0x0102（読み 2 本）にした**: 送り出し 194 → 348 Mbit/s（43.5 MB/s）、予算 20 MB/s の使用率 79 % → 46 %。2G-4 の運用の形で 30 分の照合を通過。起動時の systemd のユニットで書く（`board/`、手順は `proj001/docs/runbook.md` の 09）
- **読みを 4 本以上にすると速くはなる（403〜420）が、CPU の DDR の読みを遅くし、2G の取得が追いつかなくなる**。0x0102 より大きくしない
- 2G の束ね（n_sum > 1）の取得は 0x0101 でも 1 周 26 ms / 30.72 ms（85 %）で余裕が薄い。C の道にするのは 2G の M5 の PS の仕事（ここでの結論とは別に要る）
- 残り（急がない）: GEM の要求 1 本 ≒ 4.5 µs の遅れの出どころ・≒ 425 Mbit/s の天井
