# proj007 — 1PPS の受信とサンプルカウンタ（エポックの付与）

日付: 2026-09-17
状態: **設計**（着手前）

## 目的

45m から配られている 1PPS を PL で受け、**取得したサンプルに絶対時刻を貼れる状態**を作る。
あわせて、**取得の開始を PPS 基準の予約時刻で発火**させる。

proj007 の成果物はビットストリームではない。**「このサンプルは何時のものか」と言える状態**と、
**「次の PPS の 0.5 秒後から取る」と書けば必ずそうなる状態**の 2 つである。

積分窓の生成そのものは proj007 の範囲に入れない（下の「決めたこと」）。

## 同期の 3 層のどこにいるか

proj006 で分けた 3 層のうち、**③ を担当する**。

| 層 | 揃えるもの | 手段 | 状態 |
|---|---|---|---|
| ① 周波数 | fs の確度とボード間コヒーレンス | 外部 10 MHz → CLK_IN | **proj004 で完了**（−0.015 ppm）|
| ② サンプル位相 | タイル間 / ボード間のサンプル境界 | SYSREF / MTS | **proj006 で決着**（MTS 不要）|
| ③ **絶対時刻** | **エポック、積分窓の開始** | **1PPS** | **proj007** ← ここ |

## なぜ PPS を毎秒のトリガにしないか

**これが proj007 の設計上いちばん大きな判断である。**

素直に考えると「PPS の立ち上がりで積分を開始する」になるが、それは採らない。
**PPS は最初の 1 回だけ使い、以後はカウンタが時刻を作る。**

| 理由 | |
|---|---|
| **fs が整数** | 1,228,800,000 サンプル/秒。AXIS の 1 ビート = 8 サンプルなので **1 秒 = 153,600,000 ビートちょうど**。共通の 10 MHz にロックしていれば、一度合わせたカウンタは永久に PPS と整合する |
| **ジッタを持ち込まない** | 毎秒叩き直すと、ケーブル長差・コンパレータの遅延・その揺らぎが毎回データの時刻に乗る。1 回だけなら固定の較正定数として引ける |
| **PPS が切れても止まらない** | ホールドオーバが自然に成立する。PPS の欠落は観測の停止ではなく**フラグ**になる |
| **1 秒以外の積分時間で破綻しない** | 10 ms = 1,536,000 ビートちょうど。1 ms = 153,600 ビート。整数ミリ秒ならすべて割り切れる。PPS 再トリガ方式だと端数の始末が要る |

したがって発火条件は **`beat_count == start_at`**（カウンタ値の一致）であり、PPS は
`start_at` を決める基準点と、その後の**残差の監視**に回る。

**この形にしておくと proj008（2 台同期）がそのまま乗る。** 両ボードに同じ 10 MHz と
同じ 1PPS を配り、**同じ `start_at` を書くだけ**で 1 ビート（6.5 ns）以内に揃う。

## ハードウェア — 基板の PPS 入力の実体

出典は RFSoC 4x2 Reference Manual Rev A6（Figure 6 と Appendix A の 1PPS Control）。

SMA は基板シルクで **`PPS Clk`**。RefMan の記述は

> The RFSoC board provides two PPS signals derived from a comparator and a Schmidt trigger,
> and an 8-bit value SPI ADC.

**1 本の SMA から、基板が 2 系統のディジタル出力と 1 系統のアナログ読み出しを作って PL へ出している。**
観測所側に追加で用意するものは無い。**PPS のケーブルを `PPS Clk` に挿すだけ**である。

| 信号 | ピン | 中身 |
|---|---|---|
| `IRIG_COMP_OUT` | **AJ13** | LMV7235 コンパレータの出力（**オープンドレイン**）|
| `IRIG_TRIG_OUT` | **AH13** | シュミットトリガの出力 |
| `IRIG_ADC_SDO` | **AK13** | ADS7885S（8 bit SPI ADC）のデータ |
| `IRIG_ADC_SCLK` | **AH12** | 同 クロック |

IOSTANDARD は LVCMOS18（RefMan: PL の信号は特記なき限り LVCMOS18）。

**未確認が 4 つある。どれも実測で決める。**

1. **極性。** PPS の立ち上がりが PL 側で立ち上がりとして出るか。LMV7235 はオープンドレインで、
   反転して使われている可能性がある。→ **ソフトから極性を選べるようにして実測で決める**
2. **コンパレータの閾値。** RefMan に閾値の記載も、閾値を決める DAC / 半固定抵抗の記載も無い。
   **45m の 1PPS のレベルで受かるかどうかは、挿してみるまで分からない**
3. **`IRIG_COMP_OUT` のプルアップ。** オープンドレインなので、基板にプルアップが無ければ
   PL 側は浮く。動かなければ XDC で `PULLUP true` を当てる
4. **ADS7885S の CS_N のピン。** Appendix A のピン表に SDO と SCLK しか出てこない。
   **proj007 では SPI ADC は使わない**（後述）

### COMP と TRIG を両方取り込む

追加コストはピン 1 本と数十 LUT なので、**両方取り込んで両方にタイムスタンプを打つ**。

ただし期待値には正直でいる。**両者の差はおそらく 1 ビート（6.5 ns）未満**で、
その場合この測定が言えるのは「シュミットトリガの遅延は 6.5 ns 未満」までである。
**それでも取る価値があるのは、各系統に独立のグリッチ計数を持たせられるから**で、
「片方だけが余分なエッジを数えている」という形で波形の汚れが見える。

proj006 で「対照を並べていたから偽陽性だと分かった」のと同じ理由である。

## 設計

### 1. 時刻の実体は 64 bit のビートカウンタ

AXIS クロック（`clk_out1_system_clk_wiz_adc_0` = 153.6 MHz）で自走する。
**`aresetn` 以外では止めないし戻さない。**

| | 値 |
|---|---|
| 分解能 | 1 ビート = **6.5104 ns**（= 8 サンプル）|
| 1 秒 | **153,600,000 ビート** |
| 10 ms | 1,536,000 ビート |
| 64 bit の周回 | **約 3800 年** |
| 32 bit の周回 | 27.96 秒 |

**6.5 ns 粒度で十分**である。積分時間 10 ms〜1 s に対して 9 桁小さく、PPS 分配の
ケーブル遅延やコンパレータ遅延より細かい。**TDC やキャリーチェーンによる細分は要らない。**

### 2. `pps_capture`（新規 RTL・AXIS ドメイン）

```
 pps_trig ─▶ 3FF 同期器(ASYNC_REG) ─▶ エッジ検出 ─┬─▶ pps_stamp      ← beat_count をラッチ
                                    (極性は可変)   ├─▶ pps_count      ← 受信数
                                                   ├─▶ pps_interval   ← 前回との差（ビート）
                                                   ├─▶ ブランキング 0.5 s → pps_glitch
                                                   └─▶ 欠落検出 1.5 s  → pps_alive
 pps_comp ─▶ 3FF 同期器(ASYNC_REG) ─▶ エッジ検出 ─┴─▶ pps_stamp_comp / comp_glitch
```

**`pps_interval` がそのまま周波数確度の測定器になる。** これは proj007 の副産物だが、
副産物の方が大きいかもしれない。

| | 分解能 |
|---|---|
| proj004（53.3 µs のキャプチャ＋サブビン補間）| 0.015 ppm = **15 ppb** |
| proj007（PPS 残差を 100 s 積む）| **0.065 ppb** |
| 同 1000 s | **0.0065 ppb** |

**100 秒で 230 倍。** しかも観測中ずっと走らせられるので、proj004 で踏んだ
**「基準が切れても `PLLLockStatus` は 2 のまま 90 ppm ずれる」が恒久的に検出可能になる。**

なお 45m の 1PPS と 10 MHz が同じ標準から出ているなら、残差はフラットになるはずである。
**フラットであること自体が検証**になる。ドリフトしたら、どちらかが思っているものと違う。

### 3. 発火は `beat_count == start_at`

`capture_gate` に `trig_mode` を足す。

`trig_mode` は **`gpio_capture` の ch1 の bit 30**（`arm` の隣）に置く。
`arm` と一緒に書く値なので、別のレジスタに分けると毎回 2 回書くことになる。

| mode | 動作 |
|---|---|
| **0** | 即時（**proj006 と同一**。過去の proj の再現性を壊さないために残す）|
| **1** | `beat_count[31:0] == start_at[31:0]` で発火 |

**実装は `start_at - 1` で `trig` を出す。** `trig` の 1 クロック後に
`capture_gate` の `running` が立つので、**実際に取り始めるビートがちょうど
`start_at`** になる。1 ビットずれる実装は実機でも動いてしまい、
「ケーブル長差かソフトの遅れか」と区別がつかなくなるので、
テストベンチの判定条件を `t_start == start_at` にしてある。

ソフト側の手順:

```
snap → pps_stamp を読む
start_at = pps_stamp + k × 153_600_000     # k = 2〜3。ソフトのレイテンシぶん余裕を取る
start_at を書く → DMA を張る → arm
```

`start_at` は **32 bit で足りる**（周回 27.96 s に対して k は数秒）。

**`late` フラグを必ず持つ。** arm した時点で `start_at - beat_count` が符号付きで負なら、
発火させずに `late` を立てる。**これが無いと、ソフトが間に合わなかったときに
「2^32 ビート待つ」という止まり方をして、原因が遠くなる。**

`t_start`（実際に発火したビート）を 64 bit でラッチして読めるようにする。
**書いた `start_at` と読んだ `t_start` の下位 32 bit が完全一致することが判定条件になる。**

### 4. 読み出し — スナップショットとセレクタ

64 bit を 32 bit で 2 回読むと桁が裂ける。**`snap` の立ち上がりで全カウンタを一括ラッチ**し、
`sel` で選んで 1 語ずつ読む。`snap_ack` を返してラッチ完了を待てるようにする
（待ち時間で誤魔化さない。**壊れたときに気づける形にする**）。

**`gpio_capture` は触らない。** proj006 との diff を読めるまま保つため、AXI GPIO を 2 個足す。

| IP | ch1 | ch2 |
|---|---|---|
| `gpio_time_ctrl` | out: `start_at[31:0]` | out: 制御ビット（下表）|
| `gpio_time_stat` | in: `rdata`（`sel` で選択）| in: `flags`（下表）|

制御ビット（`gpio_time_ctrl` ch2）

| bit | |
|---|---|
| 0 | `snap` |
| 4:1 | `sel[3:0]` |
| **5** | **`pps_pol`（0 = 立ち上がり / 1 = 立ち下がり）** |
| 31:6 | 予約 |

**`pps_pol` をソフトから変えられることが重要。** 極性が未確認なので、
これが無いとビットストリームを焼き直しながら極性を探すことになる。

**TRIG 経路と COMP 経路は常に両方スタンプする**ので、「どちらを使うか」の
選択ビットは持たない。読む側が両方見て決める。

状態ビット（`gpio_time_stat` ch2 = `flags`）

| bit | |
|---|---|
| 0 | `pps_alive`（1.5 秒以内に PPS が来ている）|
| 1 | `late`（arm した時点で `start_at` が過去だった）|
| 2 | `armed`（予約を待っている）|
| 3 | `snap_ack` |
| 4 | `comp_alive` |

`gpio_capture` ch2 の `status` にも `armed`（bit 2）を足した。
bit 0 = busy / bit 1 = done は proj006 と同じ。

`sel` の割り当て

| sel | 語 |
|---|---|
| 0 / 1 | `beat_count[31:0]` / `[63:32]` |
| 2 / 3 | `pps_stamp[31:0]` / `[63:32]`（TRIG 経路）|
| 4 | `pps_count[31:0]` |
| 5 | `pps_interval[31:0]` |
| 6 / 7 | `t_start[31:0]` / `[63:32]` |
| 8 | `pps_stamp_comp[31:0]`（COMP 経路）|
| 9 | `{comp_glitch[15:0], trig_glitch[15:0]}` |
| 15 | **`0x0007_0001`（識別子）** |

**識別子を 1 語置いてある。** GPIO の結線とビットストリームの版が合っているかを
実機で 1 回の読み出しで確かめられる。**未使用の `sel` は `0xBAD0000n` を返す** —
0 を返すと「配線が死んでいる」と区別がつかない。

`flags`（`gpio_time_stat` ch2）: `pps_alive` / `late` / `armed` / `snap_ack` / `comp_alive`

### 5. PS 側で UTC の整数秒を貼る

PL が知っているのは「リセットからの PPS 数」だけである。**整数秒は PS が与える。**

- `pps_count` と `clock_gettime(CLOCK_REALTIME)` を対応づける
- **必ず秒の真ん中（x.5 s）で読む。** 秒境界をまたぐと 1 秒ずれる
- NTP が ±0.5 s 以内に入っていれば一意に決まる
- 割り込み（PL → PS IRQ）でのカーネルタイムスタンプは **proj007 ではやらない。**
  ポーリングで足りるし、割り込みを入れると「どこで遅れたか」の切り分けが増える

### 6. コンパレータ経路の遅延を ADC で測る — **proj007 の機能で proj007 を較正する**

LMV7235 の伝搬遅延はデータシート上 45 ns 級で、しかも**オーバドライブ依存**である。
実測しないと分からない。**そして測る道具は proj007 自身が作る。**

1. 1PPS を 2 分配し、片方を `PPS Clk` へ、もう片方を **10〜20 dB 減衰させて ADC 入力へ**
2. `start_at = 次の PPS の予測ビート − 4096`（26.7 µs 前）で arm し、8192 ビート（53.3 µs）取る
3. **エッジが取得窓のど真ん中に入る**ので、ADC の時間軸（0.814 ns）で直接エッジ位置が読める
4. PL のタイムスタンプとの差 = コンパレータ経路の遅延 ＋ ケーブル長差

**注意 2 つ。**

- **バラン MABA-011118 は 10 MHz〜10 GHz で DC 結合ではない。** パルスの平坦部は垂れる。
  だが**エッジは高周波成分なので通り、微分されて鋭いスパイクになる** — タイミング測定には
  かえって好都合である。「方形波が方形に見えない」で慌てないこと
- **0 dBFS ≒ +5.8 dBm（≒ 1.23 Vpp）。** TTL レベルの PPS は減衰器なしだと飽和する。
  **減衰量は proj005 の規約どおり記録する**

### 7. 極性の決め方

幅の分かっているパルス（例: 20 ms High / 980 ms Low）を入れ、
**立ち上がり〜立ち下がりのタイムスタンプ差が 20 ms になる方が真の立ち上がり**である。
`pps_pol` を 0 と 1 で切り替えて両方測れば、焼き直さずに決まる。

実 1PPS が 45m の仕様どおりの幅で出ているなら、その幅で同じ判定ができる。

## 決めたこと

- **決定**: PPS は毎秒のトリガにせず、**カウンタ値の一致（`start_at`）で発火**させる
  **理由**: 上の表のとおり。fs が整数、ジッタを持ち込まない、PPS 断で止まらない、
  1 秒以外の積分時間で破綻しない。**2 発目以降の PPS は残差の監視に使う**
  **見送った案**: PPS の立ち上がりを直接 `arm` に配る案。実装は最小だが、
  ケーブル長差とコンパレータ遅延が毎回データの時刻に乗り、**較正できる定数にならない**

- **決定**: **`IRIG_COMP_OUT` と `IRIG_TRIG_OUT` を両方取り込む**
  **理由**: 同じ SMA から基板が出している 2 系統なので、**観測所側の追加は不要**。
  コスト（ピン 1 本と数十 LUT）に対して、独立のグリッチ計数という対照が手に入る
  **正直に**: 両者のタイムスタンプ差は 1 ビート（6.5 ns）未満に埋もれる公算が高い。
  そのときこの測定が言えるのは「6.5 ns 未満」までである

- **決定**: **積分窓の生成は proj007 に入れない**
  **理由**: 窓の生成は FFT と積分器の構造（何ビン・何段・オーバーフローの扱い）に結合する。
  先に窓だけ作ると、分光計本体を組むときに必ず作り直しになる。
  **proj007 は「時刻が貼れること」と「予約時刻で発火すること」で止める**
  **見送った案**: 周期的な窓生成器（1 s / 10 ms の分周）まで入れる案

- **決定**: **`pps_pol` をソフトから切り替えられるようにする**
  **理由**: 極性が RefMan から確定できない。焼き直しながら探すのは proj004 で
  「レジスタを疑う前に信号が来ているかを測る」を踏んだのと同じ形の時間の浪費になる

- **決定**: **`start_at` は 32 bit。`beat_count` と `t_start` は 64 bit**
  **理由**: 予約は数秒先なので 27.96 s の窓で足りる。時刻そのものは
  途中で巻き戻ると後始末が面倒なので 64 bit（3800 年）にする
  **付随**: 一致検出は **上位と下位で 2 段に分ける。** 153.6 MHz（6.51 ns）で
  32 bit の一致比較は臨界経路になりうる。**proj006 の WNS は +0.588 ns しか余裕が無い**

- **決定**: **`gpio_capture` は変更せず、AXI GPIO を 2 個足す**
  **理由**: proj006 との diff が「足した分」だけになる。
  **見送った案**: `gpio_capture` の空きビット [30:24] に snap / sel を詰め込む案。
  7 ビットにちょうど収まるが、**`arm` を書くたびに `sel` も書き直すことになる**

- **決定**: **ADS7885S（SPI ADC）は proj007 では使わない**
  **理由**: CS_N のピンが Appendix A のピン表に出てこない。
  入力レベルの確認は**スペアナかオシロで基板の外で行う**方が早く、確実である
  （proj004 の「信号が来ているかを先に測る」）。
  **入れるとしたら、無人運用での入力レベル監視が欲しくなったとき**

- **決定**: `trig_mode 0`（即時）を残す
  **理由**: proj006 の測定（`slice_map.py` / `tile_offset.py`）がそのまま動く。
  **PPS 側が動かなかったときに、切り分けの基準点が残る**

## 成功の判定

1. **PPS を受けて `pps_count` が毎秒 1 増える**（= 受かることの確認。閾値と極性の決着）
2. **`pps_interval` が 153,600,000 ± 数ビートに収まり、外部 10 MHz の有無で変わる**
   （proj004 の裏取りが PPS 単独で取れる）
3. **`trig_mode 1` で発火し、`t_start[31:0]` が書いた `start_at` と完全一致する**
4. **PPS を ADC に入れた較正で、コンパレータ経路の遅延が数値で出る**
5. WNS ≥ 0

**2 と 4 が本題**で、1 と 3 はそのための道具である。

判定 1 が通らない（受からない）場合は、そこで proj007 を止めて**入力回路の調査を別に立てる**。
**「受からない」も結果**であり、その場合は外付けのレベル変換で回避する道に移る。

  - `src/capture_gate.v` に `trig_mode` / `armed` / `trig` / `started` を足した。
    **mode 0 の振る舞いは proj006 と同一**
  - `src/pps.xdc` を新規に書いた（AH13 / AJ13 / `set_false_path`）
  - `build.tcl`: AXI GPIO を 2 個追加、`smc_ctrl` を NUM_MI 3 → 5、
    `create_bd_port` で `pps_trig` / `pps_comp` を出し、
    **実装後に配置を読み返して AH13 / AJ13 でなければ止める**検査を足した
  - `pynq/pps.py` / `pynq/pps_delay.py` を新規に書き、`adc_capture.capture()` に
    `start_at` を足した
  - **`make sim` は ALL PASS**（`tb_capture_gate` = proj006 の回帰 /
    `tb_pps_capture` = 結合）。`tb_pps_capture` は失敗すると `$fatal` で
    非ゼロ終了するので `make` が止まる

- **設計で気をつけたところ**
  - **`create_bd_port` を使う。** `make_bd_pins_external` はポート名に `_0` を足すので、
    XDC の `get_ports pps_trig` と食い違う。**焼いてから「PPS が来ない」で気づく類の穴**
  - **一致検出を 2 段に分けた。** 153.6 MHz は 6.51 ns で、proj006 の WNS は
    +0.588 ns しか余裕が無い。上位 16 bit の比較は「**次の** `beat_count`」に対して
    1 クロック前に登録しておく。こうすると `start_at` の下位が 0 のとき
    （上位が桁上がりする瞬間）も破綻しない
  - **年齢カウンタは飽和させる。** 巻き戻すと `alive` の判定が壊れる
  - **テストベンチでは PPS の自動生成と手動注入を別のレジスタにした。**
    1 本の `reg` を 2 つの手続きブロックから叩くと後勝ちになり、
    グリッチ試験が黙って空振りする

## 再現手順

### ビルド（Vivado サーバ）

```bash
make sim        # テストベンチ。**Vivado もライセンスも要らない。**先にこれを通す
make            # 合成〜ビットストリーム（build/proj007.bit と .hwh）
make timing-check   # 速度グレード -1 で閉じるか（build-1-e/ に出る）
```

`make` は末尾で **1PPS のポートの配置を読み返す**。AH13 / AJ13 でなければ止まる。

### 実機（PYNQ v3.1.1）

**`make prog`（JTAG 書き込み）は使わない。** proj003 以降は `Overlay()` でロードする
（`.hwh` が無いと `ol.gpio_time_ctrl` などのドライバが生えない）。

```bash
scp build/proj007.bit build/proj007.hwh pynq/*.py xilinx@<board>:~/proj007/
ssh xilinx@<board>
cd ~/proj007

# 1. まず構成。proj006 と同じ（4ch とも PLLLockStatus = 2 であること）
sudo -E $(which python3) adc_capture.py --probe --clkin 0

# 2. PPS が受かるか。**これが判定 1。ここが通らなければ先へ進まない**
sudo -E $(which python3) pps.py --probe --clkin 0

# 3. 極性を決める（45m の 1PPS のパルス幅を --width に入れる）
sudo -E $(which python3) pps.py --pol-check --width 0.020 --clkin 0

# 4. 判定 2。残差を積んで周波数確度を出す（2 分で 0.05 ppb 級）
sudo -E $(which python3) pps.py --watch 120 --clkin 0

# 5. 判定 4。コンパレータ経路の遅延（1PPS を 2 分配して片方を ADC へ）
sudo -E $(which python3) pps_delay.py --ch 0 --trials 10 --clkin 0 --atten-db 20
```

判定 3（`t_start == start_at`）は 5 の中で毎回確かめている。
ずれていればその場で止まる。
