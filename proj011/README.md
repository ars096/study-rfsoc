# proj011 — FFT IP を realtime・資源優先に設定し直し、1ch のまま資源と `-1` の余裕を測り直す

日付: 2026-09-24
状態: 進行中（rev2 まで完了: **res は DSP 480、WNS `-2` +0.327 / `-1` +0.277（余裕 7.1 %）**。実機は未実施）

## 目的

**4ch に広げる前と、窓の切り出しの方式を選ぶ前に、「FFT 1 本にどれだけ資源を使うか」を実測で押さえる。**

proj010 は 1ch で動いたが、次の 2 つが 4ch への拡張と窓の切り出しの両方を塞いでいる:

- **DSP**: 944（22.1 %）のうち **FFT IP が 800（1 個 50 × 16）**。そのまま 4ch にすると 3776（88 %）。
  最終仕様（IF 4 本 × 1 IF あたり 2〜8 窓）で窓ごとに FFT を持つなら、さらに足りない
- **`-1` の余裕**: WNS +0.081 ns（周期 3.906 ns の 2 %）。`-2` の最悪経路は **nonrealtime を選んだために
  IP の中に生えるクロックイネーブル（CE）の大ファンアウト**（配線 97 %）だった

どちらも **IP の設定だけで手が打てる**（RTL はほぼ変えない）。この proj ではそれを試し、
FFT 1 本あたりの DSP・LUT・BRAM と、`-1` の WNS を実測で出す。その数字を持って、proj012 以降で
窓の切り出しの方式（ソフト DDC か粗い PFB か）を選ぶ。

**機能は proj010 と同じ**（ADC_B 1 本・8192 点・4096 ch × 0.5 MHz・100 ms 積分）。
proj010 の判定の道具（`make sim`・`--probe`・`--golden`・`--tone`・`--radiometer`・`--tick`）を回帰試験に使う。

## 手順

1. **`make sim`**（Vivado 不要）— spec_core の接続を 1 本外したので、proj010 と同じ 3 層（bit 単位・numpy・帳簿）で通ることを確かめる。
   モデル（`sim/lane_fft_model.v`）も出力側の tready を外した。**途切れたときの realtime の IP の振る舞いはモデルしていない**
2. **`make survey`**（新設）— FFT IP を 1 個ずつ OOC 合成し、8 通り（throttle × 乗算器 × バタフライ）の資源を
   `build-survey/survey.txt` に出す。**nonrealtime / performance / xtremedsp（= proj010）が DSP 50 になることを物差しの検証にする**
3. survey の数字で「本番」の予言（下の表の空欄）を書く — **ビルドの前に**
4. `make` と `make FFT_OPT=perf`（`-2`）、`make timing-check` と `make timing-check FFT_OPT=perf`（`-1`）
5. 実機: res の `.bit` で回帰試験（下の「実機」）

## rev2（2026-09-24）— フレーム頭の判定を前もってレジスタに置く

rev1 の最悪経路（`cur_k → t_last`、フレーム頭の 1 クロックで 32 bit の加算・比較を 2 段直列）を構造から直す。

- **幅のある演算を `pre_*` に追い出した**: `cur_k + 1`・`cur_k + 1 == run_ndump`・`cur_idx + 1`・`cur_idx + 1 == n_eff − 1`・`n_eff == 1`・`cur_idx == 0xFFFF_FFFF`。
  入力（`cur_k`・`cur_idx`・`run_ndump`・`run_n`）はフレーム頭と RUN でしか変わらず、次に読まれるまで 512 クロック（RUN からは 2 フレーム以上）あるので、1 クロック遅れで必ず間に合う
- **`fout == run_f0`（48 bit）も追い出した**: `fout` はフレーム頭の直前（k1 = 511）に進むので、同じ瞬間に `fout + 1 == run_f0` をレジスタへ取る。RUN と同じクロックでは消す（新しい `run_f0 = fin + 2` とはどのみち一致しない）
- フレーム頭に残るのは選択だけ。ID = **0x0011_02CC**。`spectrometer.py` は上位 16 bit で照合し、rev を表示する
- **`make sim`（SHIFT 7）: 全部通過。3 試験のダンプ（各 8215 行）が ID の 1 行を除いて rev1 と完全に同じ**（振る舞いを変えていないことの確認）

| `-2` の最悪経路 | `cur_k → t_last`（+0.159） | **`cur_k` からの経路は上位 5 本から消える** | 幅のある演算がフレーム頭の選択から外れた |
| WNS `-2`（res） | +0.159 | **+0.35〜+0.45** | rev1 の 2 番手（+0.387 × 4）が先頭になる。その 4 本が同じ制御の別の枝なら、もっと上がる |

### ビルド（1 回目、2026-09-24）— ポートの照合の誤りで止まった

`build.tcl` の「在ってはいけないポート」の照合が、realtime の IP に `m_axis_data_tready` が**在る**と判定して止まった。

- **IP は realtime になっていた。**照合が読み違えていた: `synth/lane_fft.vhd` には entity の宣言のほかに、
  IP コア（xfft_v9_1_x）の **component 宣言**が入っていて、そちらは設定に依らず全部のポート
  （`aclken`・`m_axis_data_tready`・`m_axis_status_*`・`event_*_channel_halt` …）を持つ。照合はファイル全体を読んでいた
- 裏づけ: エラーに出た一覧は RTL の 17 本が先に並び（entity）、その後に上の 8 本が component の宣言順で続いた。
  throttle_scheme の読み返しは realtime で通っていた
- **proj010 から在る「在るか」の照合にも同じ穴があった。**entity に無いポートでも component 側で通ってしまう。
  「在ってはいけない」側を足して初めて、照合そのものが嘘をついていたと分かった（**外れた予言が道具の誤りを出した**）
- 修正: entity lane_fft の宣言の中だけを読む。見出しに「entity の宣言から N 本」を出す（17 本が期待値）

### 実機（2026-09-25、rev2・res、外部 10 MHz）

| 判定 | 結果 | |

| 0 `--probe` | ID = 0x0011_0207（rev2 / res）。499,972 フレーム/s、FIN − FOUT の区間 [−6, 10] が 5 s おいて同じ、FLAGS 00、一括読みと 1 語ずつが一致 | **通過**（proj010 と同じ） |

**realtime の危険が実機で出た（か、それに近いもの）。**FLAGS[5] は 16 個の lane_fft の `event_tlast_unexpected` / `event_tlast_missing` の OR。
proj010（nonrealtime）の実機では一度も立っていない。`--probe`（約 7 s）と `--golden` では立たず、`--tone`（100 ms の積分を含む）で立った。
FLAGS[4]（入力の隙間）・[3]（IP が入力を受けなかった）・[0]/[1]/[7]（出力の valid・XK_INDEX の揃い）は立っていない。

FLAGS は粘着なので、次の 2 つを区別できない:

- **(a) 1 回ずれて、以後ずっと立つ** — IP の中のフレームの切れ目が、spec_core の入力側の数え（`m_in`）と 1 回ずれた。
  出力側は IP の XK_INDEX で数えるので揃ったまま（[1]/[7] が立たない）。**スペクトルは窓がずれたまま正しく見える**（線の位置も振幅も変わらない）。
  スナップショット（`m_in` 側で切る）とダンプは別の窓になるので、`--golden` の照合は落ちる
- **(b) ときどき 1 回だけ立つ** — 枠は保たれていて、IP の事象の出方の問題

- それでも分かったこと: **定常状態では 240 s 立たない** → (a)「ずれて立ち続ける」ではない（ずれていれば見張りの間ずっと立つ）
- 残る候補: **RUN の立ち上がり前後で立つ**か、**まれ**か → `--flagwatch` を直し（見張りの前に立っていたものを読んでから消す）、失敗した `--tone` をそのまま繰り返す

  定常状態の見張りは合計 5 分で 0 回

- **(a) か (b) かはまだ決まっていない。**立った 1 回は、その後の持続を見る前に Overlay を読み直していた
- 次: 起動を 20 回繰り返して（各回 `--flagwatch 10 --flagwatch-run 50000`）、proj011 と proj010（対照）で起動あたりの率を比べる。
  定常状態の率は 1 時間の `--record`（flags_or）で見る

**3 回目: 起動 20 回ずつの比較（各回 `--flagwatch 10 --flagwatch-run 50000`）**

| | 起動 20 回のうち FLAGS[5] が立った回 | 立ったときの形 | 事象の後の照合（`--golden` と同じ） |
|---|---|---|---|
| **proj011 rev2（realtime）** | **7 回**（8・9・11・12・13・18・19 回目） | **7 回とも、見張りの前から立っていて、消しても 10 ms 後にまた立つ。10 s 中ずっと**（0.05 s おきに読んだ 166 回すべて） | **7 回とも OK** |
| **proj010（nonrealtime、対照）** | **0 回** | — | — |
| （参考）立たなかった起動 | 13 回。10 s の間 1 回も立たない | | |

- **realtime が原因と決まった。**同じ率（7/20）なら proj010 で 20 回とも立たない確率は 0.65^20 ≒ 2e-4
- **起動ごとの二択。**立つ起動では立ち上がりから最後まで立ち続け、立たない起動では一度も立たない。途中で立つことも止まることもない
  → 起動（リセットの解除と入力の始まり）のどこかで状態が決まり、以後固定される
- **「立ち続ける」は予言 (a) の形だが、中身は (a) ではない。**(a) なら IP のフレームの切れ目が spec_core の入力側の数え（`m_in`）とずれて、
  スナップショット（`m_in` で切る）とダンプ（IP の出力）が別の窓になり、照合が落ちるはず。**7 回とも照合は通った**（入力は雑音なので、1 サンプルでもずれれば落ちる）。
  **IP が実際に FFT に切っている枠は正しく、IP の TLAST の検査だけが別の位置を「フレームの終わり」と思っている**
- 「事象の間隔 30,000〜35,000 フレーム」は読み出しの間隔（0.06 s）を数えているだけで、事象の周期ではない
- 見立て（未確認）: realtime の IP は、TLAST を照合する数えと実際の枠の数えが別で、リセットの解除と最初の `tvalid` の相対位置で
  前者の起点がずれることがある。nonrealtime は入力を待つので両者が一つになる

**まだ分からないこと**: 16 本のうち何本で立つか／unexpected か missing か／ずれの量。FLAGS[5] は 16 本 × 2 種の OR なので、今の RTL では読めない
