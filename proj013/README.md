# proj013 — 全帯域の total power を 1 ms ごとに取る（4 IF）

日付: 2026-09-28
状態: **進行中**（sim-all 8 本通過・`-2` +0.205 / `-1` +0.170 で閉じた。PS 側の `--tp` は模擬で確認、実機は未）

## 目的

**4 本の IF それぞれで、全帯域（2 GHz）の電力 Σx² を 1 ms ごとに取り、スペクトルと同じフレーム番号の上に並べる。**

- 連続波・total power の観測に要る（SAM45 の代替として、分光と同時に全帯域の電力を持つ）
- 持ち越しの切り分けに使う: 判定 3 の 1 s 以上のちらつき（100 ms のダンプでしか見ていない）と、判定 1 のタイル間の差 0.27 dB が時間で動くか
- **窓の切り出し（proj014 以降）の前に置く。**窓の方式に依らず接続点（ギアボックスの出口）が変わらず、先に入れて資源と `-1` を実測すれば、窓はその残りで設計できる

土台は proj012 rev3（4 本とも判定 0・2・5 通過、`-1` WNS +0.070 ns）。1 本ずつの分光計は proj012 rev3 と同一で、proj012 の判定を回帰試験に使う。

## tp_core の作り（proj012 rev3 の `-1` の最悪経路から）

```
s0  フレームの頭の判定（pre_*: 48 bit の比較は前のクロックにレジスタへ）
s1  入力を 1 回だけ受ける（x = tdata >>> 2、16 レーン）
s2  s3  DSP の入口のレジスタ 2 段（AREG/BREG = 2）
s4  s5  x² → M → P（DSP 16 個 / ch）
s6..s9  加算木 16 → 8 → 4 → 2 → 1（1 段ごとにレジスタ）
s10 区切りの和（64 bit）  s11 リングバッファ（BRAM）へ
```

- **ファブリックの加算から DSP の入口へ直につながない**（群 A・B の形を作らない）
- spec_core の入力（s_axis_tdata）に足すファンアウトは s1 の 256 本だけ
- 区切りの判定は `fcur ≥ TP_N − 1`（等号にしない。F0 を取りこぼしたまま TP_N を小さくすると区切りが止まることを、単体の sim の陽性対照で見つけた）

## やったこと

- proj012 の追跡ファイルを複製（`git ls-files proj012`）。ID・proj の名前・BITFILE を proj013 に
- `src/tp_core.v` を書き、spec_core につないだ
- 単体の sim（`make sim-tp`）: 模型は RTL の写しではなく仕様（tp_core.v の冒頭）から書いた。試験は自走（TP_N 3）→ TP_N 1 で RUN（530 個でリングバッファが一巡）→ TP_N 4 で RUN。**RUN の F0 の頭の直前には必ず 3 クロックの隙間**を入れた（F0 の判定の急所）
  - 1 回目で通過。陽性対照（隙間を考えない F0 の判定）を入れると、F0 を取りこぼした後 **TP_WP が 7 で止まった**。TP_N を 4 → 1 に下げると `fcur == TP_N−1` が二度と成り立たないため → 判定を `≥` にした
  - `≥` にすると陽性対照が**通ってしまった**。RUN で始まった区切りが最後の 512 個の外に出ていた → 試験の順序を入れ替え、「最後の 512 個の中に F0 で始まった区切りと短い区切りがある」ことも判定に足した。今は本番が通過・陽性対照が落ちる

## PS 側の total power（2026-09-29、`pynq/spectrometer.py --tp SEC`）

- 選んだ ch を**同時に**読む（`--ch all` が既定。TP-5 の ch 間の相関のため）。TP_N を書き、RUN を 4 本続けて打ち、SEC 秒のあいだ 20 ms ごとに読む
- 読み方（`TpReader`）: TP_WP → 前回からの個 → TP_WP の挟み読み。**読み直した TP_WP が「前回の続き + 512」を越えたら読み落とし**として数える。
  最初は F0 の個（FLAGS[1] が立ち、番号 = RUN_F0）を探し、それより前の個は捨てる。フレームの番号は下位 32 bit を前の個から伸ばす（2.4 時間で巻き戻るため）
- スペクトルも同時に回し（N_ACC = `--nacc`、既定 50000 = TP 100 個）、閉じたダンプごとに (2 Σspec − spec[0]) · 4^SHIFT を残して、最後にパーセバルで照合する（`--tp-no-spec` で省く）
- 判定: **TP-0**（TP_PARAM・TP_F0 = RUN_F0・TP_NEFF）/ **TP-4**（読み落とし 0・番号の飛び 0・F0 の後の FLAGS 0・フレーム数 = TP_N）/
  **TP-1**（パーセバル |1 − r| ≦ 1e-3。飽和・FLAGS のあるダンプは除く）/ **TP-2**（情報: 1 ms の相対の揺れと、1〜5000 ms に束ねた揺れを √(2 / (8192·TP_N·m)) と比べる）/ **TP-5**（情報: 1 ms・100 ms の ch 間の相関）
- `--out PREFIX` で `PREFIX.tp.npz`（ch ごとの個の番号・フレーム数・和・FLAGS、ダンプの F0 と和）
- **模擬 `tools/tp_mock.py`**（MMIO を Python で模し、時刻からフレームを進めて tp_core のリングバッファと spec_core のダンプを作る。Spec と tp_run をそのまま動かす）:
  本番 OK・陽性対照 3 通り（個の番号を 1 つずらす / 読み出しの途中で 0.7 s 止まる / スペクトルの和を 2e-3 小さくする）がどれも NG、で**全部通過**。
  模擬の雑音で TP-2 の比は 0.96〜1.04（1〜20 ms）、パーセバルは模擬に入れた 2e-5 をそのまま読んだ
  - 1 個の番号がずれると「番号の飛び」は 2 と数える（ずれた個と、その次の個）。読み落としがあるとその直後の個も飛びとして数える。どちらも NG の判定には効くが、件数は事象の数ではない
  - 照合できないダンプ（個が欠けた・ずれた）はパーセバルから除き、「照合できたダンプ n / 全体」を出す

## 結果

### 実機 1 回目（2026-09-29、`--probe` と `--tp 10`、出荷時のクロック源、ADC_A に何かが入り B・C・D は未接続）

- **`--probe`: 4 本とも判定 0 通過**（proj012 の回帰。起動の途切れ 0・FLAGS 00・読み出し 4 本で 8.4 ms）
- `--tp 10`: **TP-0 は 4 本とも OK**（TP_PARAM・TP_F0 = RUN_F0・TP_NEFF 500。RUN の開始のずれ +5・+13・+18 フレーム）。読み出し 1 回（4 本の TP）中央値 1.94 ms

| ch | 平均電力 | TP-4 | TP-1 の 1 − r | TP-2（1 ms の揺れ / 理想の比）| 1 s に束ねた揺れ |
|---|---|---|---|---|---|
| ADC_A | −26.0 dBFS | 読み落とし 1 → NG | −4.0e-6〜−3.4e-6 | 2.55e-3 / 3.65 | 2.9e-4（比 13） |
| ADC_B | −60.0 dBFS | 読み落とし 1 → NG | +1.9e-2〜+3.1e-2 → NG | 1.68e-2 / 24 | 7.2e-3 |
| ADC_C | −60.4 dBFS | 読み落とし 1 → NG | +5.8e-3〜+1.9e-2 → NG | 7.9e-3 / 11 | 4.0e-3 |
| ADC_D | −58.5 dBFS | OK | +1.6e-2〜+2.6e-2 → NG | 3.4e-2 / 49 | 2.0e-2 |

- **TP-4 の「読み落とし 1 個」は PS 側の道具の誤り**: 初回の読み出しでリングバッファの 512 個を全部読みにいき、読んでいる間に進んだ 1 個（F0 より前の捨てる個）を数えた。
  D だけ 0 なのは、読み出しがたまたま 1 ms に収まったため。**初回は直近 64 個だけ読み、F0 より前の読み落としは数えない**ように直した
- **TP-1 は信号のある A だけ通り、未接続の B・C・D は 1 − r = +0.6〜3 % で落ちた。**1 − r が正 = ダンプに無いナイキストの ch（X_4096 = fs/2）に電力がある。
  見立て: RF-ADC の 8 並列インタリーブは入力なしでも k·fs/8 に線を出し、fs/2 はその k = 4。−60 dBFS しかない ch では全電力の数 % になりうる。
  **確かめるため、ダンプごとにスナップショットから X_4096 を直接出し（q）、1 − r − q で判定する**ように直した。k·fs/8 の ch（DC・1024・2048・3072）の割合と、線を除いた揺れも出す
- **TP-2: 未接続の ch の揺れは理想の 11〜49 倍で、束ねても下がらない**（1 ms〜1 s で 1〜3 % のまま）。判定 3（proj010）の「0.1〜3 s で一定のちらつき」と同じ形。
  見立て: 上の線の強さが背景較正に合わせてゆっくり動く。線を除いた揺れが理想（100 ms で 7e-5）まで下がれば当たり
- A の入力の素性（何を入れたか）は未記録 → 記録する

| A | −26.0 dBFS | **OK** | −4.0e-6〜−3.5e-6 | 4e-11〜4e-7 | 3.8e-6 | 3.40e-4 → 3.40e-4 |
| B | −60.5 dBFS | **OK** | +3.7e-3〜+1.0e-2 | 1.8e-3〜1.8e-2 | 9.6e-2 | 1.76e-2 → 4.27e-3 |
| C | −60.4 dBFS | **OK** | +8.6e-3〜+1.0e-2 | 6.1e-3〜1.8e-2 | 2.7e-2 | 4.16e-3 → 4.27e-3 |
| D | −58.4 dBFS | **OK** | +1.7e-2〜+3.1e-2 | 1.6e-2〜3.9e-2 | **3.6e-1** | 2.67e-2 → 5.93e-3 |

- **TP-4 は 4 本とも OK**（読み落とし 0・番号の飛び 0。10 秒・約 1 万個）。読み出し 1 回（4 本）中央値 2.0 ms・最大 4.1 ms
- **TP-1: 1 − r は平均ではナイキストの割合 q と揃うが、1 対 1 では ±9e-3 ずれた。**C では 1 − r がほとんど動かない（8.6e-3〜1.0e-2）のに、q は 3 倍の幅で揺れる
  → **fs/2 の成分は安定した線ではなくフレームごとに大きく揺れ、平均だけが安定している**。1 フレームの q を 50000 フレームの平均と比べた判定の作りの誤り。
  **判定は平均どうし（許容 max(1e-3, 3 × q の標準誤差)）に直した**
- **「線を除いた揺れ」は q の揺れで汚れていた**（除いた後の 4〜6e-3 は 1 フレームの q の揺れと同じ大きさ）。**ナイキストは差し引かず、ダンプの中の線だけを除く**ように直した。
  それでも B・D は線を除くと 100 ms の揺れが 1/4 ほどに下がった（上の表。ナイキスト込みの暫定）。**D では DC と k·fs/8 の 7 ch だけで全電力の 36 %**
- **A（CW）の揺れは線でも熱雑音でもない**: −26 dBFS の正弦波に ADC の雑音（≒ 30 LSB²）が乗るだけなら 1 ms の揺れは ≒ 2e-5（信号 × 雑音の交差項）。実測 2.5e-3 は 100 倍以上で、
  1 s に束ねても 2.3e-4。**SG の振幅の揺れか ADC の利得の揺れ**。同じ SG を 4 分配して 4 本に入れ、ch 間の相関（TP-5）で分ける
- 揺れの元の ch を直接見るため `--tp-save-spec`（ダンプのスペクトルとスナップショットを .tp.npz に。ch ごとに 600 ダンプまで）と
  `tools/tp_spec_analyze.py`（全体の揺れを ch ごとの寄与 c_k = w_k cov(S_k, T) / var(T) に分ける）を足した

- **B・D の揺れは DC がほとんど全部**（寄与 0.86・1.02）。D では全電力の 29 % が DC で、その DC が 100 ms ごとに ±12 % 動く。C は DC と k·fs/8 で 43 %、残りは広い帯域
- DC・k·fs/8・fs/2 はどれも 8 並列インタリーブのオフセットの線（入力と関係なく出る）。**RF-ADC のオフセットの背景較正に合わせて動いている**と読む（未検証）
- **ナイキスト（fs/2）にも位相の決まった線がある**: X_4096 の符号付きの平均が B +0.07・C +0.11・D +0.17（0 から離れる）。その上で 1 フレームごとの q は大きく揺れる（標準偏差 / 平均 ≒ 0.3）
- **判定 3（proj010）の「1 s 以上の超過・0.1〜3 s で一定のちらつき」の正体の第一候補**: proj010 は ADC 自身の雑音（入力なし）で測っていた。そのときの電力の大部分が DC とインタリーブの線だった可能性が高い。
  **実入力（増幅した雑音）でやり直すという持ち越しが要る理由がはっきりした**
- **運用の入力レベルでは効かない**: A（−26 dBFS）では DC の割合 1.5e-6・k·fs/8 の 7 ch で 4e-6。ちらつきは電力の比で効くので、入力が 30 dB 強ければ 1/1000 になる
- **A（SG の CW）の揺れは、線そのものの強さの揺れ**（ch 2192 の寄与 +0.98、隣の ch の裾も同じ ≒ 5e-4 で揺れる）。SG の振幅の揺れか ADC の利得の揺れ → 4 分配で分ける
- **TP-1（平均どうし）: A は 1 − r = −3.7e-6 で OK（信号のある ch で total power とスペクトルが 4e-6 で一致）。**未接続の B・C は 1 − r の平均が q の平均より 2e-3 小さく NG、D は 1.3e-3 で境目。
  q は 1 フレームずつの比の平均で、DC が大きく動く ch では「比の平均」と「平均の比」が食い違いうる → `tp_spec_analyze.py` に両方を出すようにした（未確認）。**未接続の ch の TP-1 は保留**
- TP-4 は 4 本とも OK（30 秒・約 3 万個）。読み出し 1 回（4 本）中央値 1.9 ms・最大 6.2 ms
- RTL の選択肢（未決）: 区切りごとに Σx も積めば、区切りの中の DC の電力 (Σx)² / N を差し引ける（加算木 1 本と 1 語）。運用のレベルで DC が 1e-6 なら要らない。増幅した雑音で測ってから決める

### 実機 4 回目（2026-09-29、熱雑音を 4 分配、`--tp 60 --out tp_noise --tp-save-spec`）

構成: **熱雑音 → 4 分配 → ADC_A〜D**（雑音源・アンプ・フィルタ・分配器・ケーブルの型番と長さは未記録 → 記録する）。入力 std ≒ 26 LSB、**−47 dBFS**（ADC 自身の雑音 ≒ 30 LSB² は全電力の約 4.5 %）

- DC と k·fs/8 の線の寄与は 4 本とも ≒ 0（全電力の 0.28〜0.36 %）。**3 回目の DC のちらつきは、入力があれば効かない**ことを確かめた

- **揺れ（1 ms 7〜28e-3、理想の 10〜39 倍）の元は、ch 1632〜1652（IF 3270〜3280 MHz）に 4 本とも出る間欠的な信号**: 上位 8 ch の寄与 0.65〜0.94。

  突き止めたものと同じ周波数帯（携帯電話の 800 MHz 帯の上り 815〜845 MHz に入る）。ADC の前に 2〜4 GHz の帯域フィルタが無ければ、ゾーン 1 の混信はそのまま載る。

- ch 間の比: A / B は 1 ms 1.5e-3 → 1 s 9.0e-4（単独の 1/5〜1/4。A・B は混信の強さがほぼ同じで打ち消し合う）。C・D を含む比は混信の強さの違いが残って大きい
- `tools/tp_spec_analyze.py --exclude 1620:1670` を足した（その ch を除いた残りの揺れと、除いた ch の電力の間欠性。ゾーン 1 の周波数も出す）

  中央値の 3 倍を越えるダンプは 0.5〜1.3 %（599 個中 3〜8 個）→ **ふだんは無く、まれに強く出る間欠的な混信**（携帯電話の上りの読みと合う）
- 除いた残りの 100 ms の揺れ: A 2.85e-3・B 2.37e-3・C 1.97e-3・D 6.6e-4（理想 7e-5 の 9〜41 倍）。**4 本で 4 倍違うので、4 本に共通の入力側の揺れだけでは説明できない**。

#### `-1` の最悪経路（`make worst-paths PART=xczu48dr-ffvg1517-1-e WP_N=3000 WP_THR=0.30`、照合の問題 0 件）

setup の slack < 0.30 ns は **218 本・すべて配線型**。群は proj012 rev3 と同じ顔ぶれで、**最悪の ch が入れ替わった**:

| 群 | proj012 rev3（`-1`） | proj013 rev1（`-1`） |
|---|---|---|
| A ひねり係数の乗算 → DFT の中の DSP | **+0.070**（spec_core_2） | **+0.170**（spec_core_2）・+0.185 |
| B DFT の最終段 → 電力の DSP | +0.103（spec_core_1） | +0.186（spec_core_2、m_re_reg） |
| C gb_fifo の書き込みアドレス FO 888 | +0.146（**gb_fifo_0**） | +0.172（**gb_fifo_1**）・+0.230（gb_fifo_3） |
| D gb_up の state_reg FO 195 → r0_data（新しく上位に） | — | +0.174（gb_up_0）・+0.203（gb_up_1） |
| E spec_core の fin → スナップショットの BRAM（新しく上位に） | — | +0.178（spec_core_3。snap_hit の 48 bit の比較） |

- **WNS が +0.07 → +0.17 に上がったのは、tp_core がタイミングを良くしたからではない。**同じ形の群が +0.17〜+0.23 に 5 つ並び、配置の組み替わりで +0.07 の 1 本が救われただけと読む。
  C の最悪が gb_fifo_0 → gb_fifo_1 に移ったのも同じ（配置で最悪の ch が入れ替わる）。**次に何かを足せば +0.07 付近に戻りうる**ものとして扱う
- 予言の外れの中身は「±0.1 ns の幅が、配置のばらつきより狭かった」。proj012 rev3 → proj013 rev1 で +0.100 動いた（proj011 では −0.167）。**次の予言は ±0.2 ns の幅で書く**
- D・E は proj012 rev3 では 0.20 ns 未満に出ていなかった。D はギアボックスの AXIS upsizer の状態の大ファンアウト、E はスナップショットの予約の比較で、どちらも tp_core とは別の場所
- **DSP の +8 は直さない。**`t8` に `(* use_dsp = "no" *)` を付ければ 8 個 / ch（計 32、全体の 0.75 %）をファブリックに戻せるが、
  代わりに LUT・CARRY8 が増え、配置も組み替わる。窓の予算では DSP と LUT がほぼ同じ速さで埋まる（proj011）ので得にならず、
  閉じている配置を崩す理由にもならない。**次の予言に効く教訓**: DSP の出口どうしの加算にレジスタを付けると、合成はそれも DSP に載せる。
  窓の切り出し（FIR の和・DDC の加算）で DSP を数えるときは、加算木の最初の段を DSP 側に数える
- hold は +0.009〜+0.019 に並ぶ（配線ツールの hold 修正の跡）。u_tp の中の hold も同じ並び
