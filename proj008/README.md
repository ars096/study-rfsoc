# proj008 — 1PPS を ADC に常時入れる構成（エポックごとの較正器）

日付: 2026-09-18
状態: **進行中**

## 目的

**較正定数を事前に測って持つのをやめ、その場で測る器を常設する。**

proj007 で `L_adc − D_pps` は装置の定数ではなく**エポックごとの定数**だと決着した。
だとすれば、較正値を記録して持ち回る設計は成立しない。**1PPS を ADC のチャネルに
常時入れておけば、1 回のキャプチャ（53 µs）が N も k も δ もまとめて与える。**

proj008 ① の成果物はビットストリームではない。**「バッファの添字 i のサンプルは何時のものか」
を、エポックが変わっても人手を介さずに答えられる状態**である。

2 台でのボード間同期（10 MHz + 1PPS の分配）は **proj009 以降に回す**。

## proj007 との差

**RTL は proj007 rev2 から変えない。** proj007 のビットストリームは既に 4ch 構成
（`chans = {0 0} {0 2} {2 0} {2 2}`）で、`epoch` と `mmcm_locked` も出ている。
proj008 で足すのは **RF の配り方**と **PS 側のソフト層**の 2 つだけ。

| | proj007 | proj008 |
|---|---|---|
| RTL | — | **同一**（`MAGIC` の番号だけ `0x0008_0001` に進める）|
| PPS の入れ先 | `PPS Clk` ＋ 判定 4 のときだけ ADC_D | **`PPS Clk` ＋ ADC 4ch 全部**（構成 A）|
| 較正 | 人が `pps_delay.py` を叩いて読む | **`epoch` の変化を検出して自動で取り直す** |
| 出口 | 較正定数の数値 | **「添字 i は何時か」を返す層** |

`MAGIC` を進めるのは、RTL が同一でも**実機に載っているのがどちらの proj のビットストリームか**を
1 回の読み出しで言えるようにするため。番号が同じだと、取り違えても症状が出ない。

## 同期の 3 層のどこにいるか

proj006 で分けた 3 層のうち ③ を **運用できる形にする**のが proj008 ①。

| 層 | 揃えるもの | 手段 | 状態 |
|---|---|---|---|
| ① 周波数 | fs の確度とボード間コヒーレンス | 外部 10 MHz → CLK_IN | **proj004 で完了**（−0.015 ppm）|
| ② サンプル位相 | タイル間 / ボード間のサンプル境界 | SYSREF / MTS | **proj006 で決着**（MTS 不要）|
| ③ 絶対時刻 | エポック、積分窓の開始 | 1PPS | proj007 で**成立**／proj008 で**常設化** ← ここ |

## 構成

### 構成 A — 較正器の特性把握（proj008 ① の本題）

**4ch すべてに同じ 1PPS を入れる。** 科学信号は取らない。**特性把握のための構成であり、
運用形ではない。**

```
1PPS ─┬─(2分配 −3 dB)──────────────────────▶ PPS Clk  （コンパレータ／シュミットトリガ）
      └─(2分配 −3 dB)─ 4分配(−6 dB) ─┬─(減衰)─▶ ADC_A   ch3
                                      ├─(減衰)─▶ ADC_B   ch2
                                      ├─(減衰)─▶ ADC_C   ch1
                                      └─(減衰)─▶ ADC_D   ch0
```

**段を分ける理由。** proj007 で受かった実績は「2 分配（−3 dB）で +2.5 V の 1PPS」である。
5 分配にすると `PPS Clk` 側が −7 dB まで落ちる。**コンパレータの閾値は RefMan に記載が無く
未文書なので、受かるかどうかは実測でしか分からない。** 段を分ければ `PPS Clk` 側は
proj007 と同じレベルのままで、変更点が ADC 側だけになる。

**ADC 側の分配損はコストではない。** 0 dBFS ≒ +5.8 dBm に対して TTL レベルの PPS は
どのみち 20 dB 級の減衰が要るので、分配の −9 dB は減衰器の置き換えになるだけである。

**4 本のケーブルは同じ長さ・同じ種類で揃える。** 揃っていれば ch 間の差はケーブルに
由来しない。揃えられない場合は長さを記録する（proj007 の実測で **1 ns ≒ 25 cm**、短縮率 0.85）。

### 構成 B — 運用形（proj008 ① の出口で決める）

科学チャネルを何本残せるかは、構成 A の測定結果で決まる。**先に決めない。**

| 案 | 科学 ch | 成立条件 |
|---|---|---|
| PPS 1 本（ADC_D）| 3 | **タイルをまたいでも 1 本で較正できること** |
| PPS 2 本（ADC_D と ADC_B）| 2 | タイル内は 1 本で足りること |

proj006 の実測（**タイル内は 0.02 サンプル以内で不変、タイル間は 1〜1.5 サンプル RMS で
起動ごとに変わる**）を素直に読めば **2 本案**になる。だが proj006 が測ったのは CW トーンの
位相であって、PPS のエッジではない。**別の量かもしれないので、測ってから決める。**

## 設計

### 1. 4ch を 1 キャプチャで同時に読む

512 bit 語に 4ch すべてが入っている。**追加のキャプチャは要らない。**

| ch（512bit 語。ch0 が最下位）| SMA | Tile / slice | `blocks[]` |
|---|---|---|---|
| 0 | ADC_D | 224 / 0 | `adc_tiles[0].blocks[0]` |
| 1 | ADC_C | 224 / 2 | `adc_tiles[0].blocks[1]` |
| 2 | ADC_B | 226 / 0 | `adc_tiles[2].blocks[0]` |
| 3 | ADC_A | 226 / 2 | `adc_tiles[2].blocks[1]` |

**1 キャプチャが 4 つの独立な測定になる。** これは対照が構成に組み込まれている状態で、
proj006 で「対照を並べていたから偽陽性だと分かった」のと同じ形である。

**Tile 224 と Tile 226 は入力極性が反転している**（proj006 で確定・厳密な 180°・周波数非依存）。
**PPS のエッジのスパイクは ch0/ch1 と ch2/ch3 で符号が逆に出る。**

**エッジ探索は壊れない。** `find_edge` は `np.abs()` を取ってから探すので、
極性が反転しても同じ位置を返す（`sim/test_analysis.py` で検証済み）。
むしろ **ピークの符号が無料の対照になる** — タイルで符号が分かれなければ、
配線か ch の対応表を疑う。`pps_delay.py` は符号を毎回表示する。

### 2. 較正の式

proj007 で確定した形をそのまま使う。

```
L_adc − D_pps = N(epoch) × 6.5104 ns + frac(overlay)
```

| | 動くもの | 測り直しの契機 |
|---|---|---|
| タイル再起動（同じ Overlay 内）| **整数ビート N だけ** | `epoch` の増加 |
| Overlay の焼き直し | **N も k も δ も** | Overlay のロード |

**実務では区別しなくてよい。** 1 キャプチャが N も k も δ もまとめて与えるので、
「エポックが変わったら測り直す」の一手で足りる。`epoch` はその瞬間を教える印である。

### 3. ch 間の差は試行ごとに対にする

**4ch は同じキャプチャの同じ PL スタンプから出ている。** したがって

- ビート量子化の固定バイアス（0〜6.51 ns。proj007 で「回数を増やしても消えない」と書いたもの）
- ±1 ビートのディザ
- PPS そのもののジッタ

は**すべて共通項として引き算で消える**。個々の ch の σ で差の誤差を見積もると、
**実際より 1 桁悪く見える。**

**判定 3 / 4 は絶対値ではなく差で見る。** これは 4ch 同時取得にした副産物だが、
副産物のほうが大きいかもしれない — proj007 が「量子化の下限は 6.51 ns で、
これは回数を増やしても消えない」と正直に書いた壁が、**差については存在しない。**

### 4. ±1 ビートのディザを潰さない

proj007 で 4 回中 2 回、±1 ビートちょうどのディザが出た。**素朴な平均は 2 つの山の間に落ちて、
どちらの山にも対応しない値を返す。** しかも σ が膨らむので「精度が悪い」ように見えるが、
実際の精度は 0.2 ns である。

`pps_delay.py` の `beat_summary()`（中央値からのビート単位のずれで分類し、多数派の山だけを返す）を
**ch ごとに掛ける。** 4ch をまとめて平均しない。

**ディザの有無はそのエポックの位相が良いかの指標になる**ので、抑えずに記録する。

### 5. 時刻を返す層

```
t(i) = t_epoch_base + (beat_start × 8 + i) × T_sample + (L_adc − D_pps)
```

呼ぶ側が意識するのは `t(i)` だけ。`epoch` の監視と再較正は層の内側に隠す。

- `epoch` を読み、**前回の較正時と変わっていたら較正を取り直す**
- 較正を取り直せない状態（`pps_alive` = 0）なら、**古い較正で黙って答えない。**
  時刻に「較正がどのエポックのものか」を添えて返し、不一致なら例外にする
- `mmcm_locked` = 0 は較正の失効と同じ扱い

**「答えを返さない」を実装すること。** proj007 で踏んだ穴の大半は「動いているように見える」形
だった。較正が失効したまま尤もらしい時刻を返す層は、同じ形の失敗になる。

## 決めたこと

- **決定**: proj008 ① では **RTL を変更しない**
  **理由**: proj007 rev2 の 4ch 構成と `epoch` / `mmcm_locked` で必要なものは揃っている。
  RTL を触ると「ソフト層の問題か RTL の問題か」の切り分けが増える。
  **`MAGIC` の番号だけは進める** — 実機に載っている版を 1 読みで言えなくなるため
  **見送った案**: PPS 欠落の sticky 記録（最大 `pps_interval`、欠落回数）を RTL に足す案。
  長時間監視のポーリング間隔を緩められるが、**持続性検証で実際に欠落が出てから入れる**

- **決定**: 較正専用の構成 A と運用形の構成 B を**分ける**
  **理由**: 4ch 全部に PPS を入れる構成では科学信号が取れない。これは**特性把握のための
  構成**であって運用形ではない。混同すると「較正のために科学 ch を 4 本潰す」設計に見える
  **狙い**: 構成 A の測定が、そのまま構成 B の割り当て（PPS 何本か）の根拠になる

- **決定**: 分配は**段を分ける**（`PPS Clk` へ −3 dB、ADC 側へ −3 −6 dB）
  **理由**: `PPS Clk` 側を proj007 で受かった実績と同じレベルに保つ。コンパレータの閾値が
  未文書なので、**分配を増やした結果として判定 1 が落ちると、原因がレベルなのか別の要因なのか
  切り分けに戻る**
  **見送った案**: 5 分配を 1 段で作る案。配線は簡単だが `PPS Clk` が −7 dB になる

- **決定**: 4ch のエッジ位置は **ch ごとに `beat_summary()` を掛ける**。まとめて平均しない
  **理由**: proj006 の「位相の巻き戻る量に算術平均を使って誤判定を出しかけた」、
  proj007 の「±1 ビートのディザを素朴な平均が潰した」と同じ形。**壊れた統計は
  壊れたこと自体を隠す**

- **決定**: 解析側の判定の分岐を **`make sim` で通す**（`sim/test_analysis.py`）
  **理由**: proj008 の結論を出すのは `epoch_verdict` の分岐だが、これは実機でしか通らない。
  放っておくと**一度も走ったことのないコードが結論を印字する**。
  proj007 で踏んだ 8 件はすべて「動いているように見える」形だった
  **効いた**: 書いた直後のテストで、`epoch_verdict` が numpy の `bool_` を返していて
  `is True` に一致しない件が出た。**値は正しいので実機では気づけない種類の誤り**である
  **訂正（2026-09-18）**: 当初 `sim` に含めたが、**Vivado サーバに numpy が無くて
  `make sim` が落ちた**。ビルド専用の機械に numpy を入れる筋合いは無いので `sim` から外し、
  代わりに `sim` の末尾で「解析側は含まれていない」を毎回明示することにした。
  **「numpy が無いので skip」は採らない** — 通らなかったものを成功として報告する形は、
  `make build` の空振りと同じ穴である

どちらが間違っているかはこの判定だけでは決まらない — それも結果として記録する。

| CDC-1 / 3 / 10 / 11 | 61 / 29 / 32 / 3 | **61 / 29 / 32 / 3** | **完全一致** |

### **最初の見立て（外れ）**

**「RTL が同一なので WNS は +0.235 ns のまま。動いたらそれ自体が異常の印」と予言した。**
実際は **+0.245 ns** で、+0.010 ns 動いた。

**ずれた理由は、自分の変更を勘定に入れていなかったこと。**
「RTL は proj007 rev2 と同一」と「`MAGIC` だけ番号を進める」を同じ息で書いていたが、
**`MAGIC` は RTL の中の定数である。** `32'h0007_0002` → `32'h0008_0001` はビットパターンが
違うので、`rdata` のマルチプレクサを駆動する LUT の定数が変わる。加えて `set proj proj008` で
プロジェクト名（= インスタンス名）が変わり、Vivado の配置・配線は名前順のタイブレークを
使う。**どちらも「設計は同じ」と言いながら配置を変える。**

### **【新しい規約】「同一のはず」の確認に WNS を使わない**

WNS は配置のタイブレークで簡単に動くので、**同一性の指標として弱い。**
一方 **CDC の分類別件数（61/29/32/3）は 4 つとも完全に一致した。**
BRAM・クロック・解析対象 0 本・asynchronous 7 箇所も一致している。

**構造の指紋で確かめること。** proj007 で「直ったことは件数ではなく分類の移動で確認した」と
書いたのと同じ道具が、ここでは逆向き（**変わっていないことの確認**）に効いた。

| 指標 | 同一性の確認に使えるか |
|---|---|
| **CDC の分類別件数** | **使える。** 構造が変われば必ず動く |
| **BRAM / LUT の使用量** | **使える。** 論理量の指紋 |
| 解析対象の経路数・asynchronous の箇所数 | 使える。制約の効き方の指紋 |
| **WNS / WHS** | **使えない。** 名前順のタイブレークで動く |
| 最悪経路のクロック | 使えない（下記）|

### 5 本目が AXIS に移った件

proj007 は「**AXIS 153.6 MHz の経路は上位 5 に 1 本も出てこない**」と書き、
一致検出を 2 段に割った判断が効いている証拠とした。proj008 では 5 本目が
AXIS（`clk_out1_system_clk_wiz_adc_0`）の **+0.766 ns** になっている。

**判断が覆ったわけではない。** +0.766 ns は最悪経路 +0.245 ns の 3 倍の余裕で、
「AXIS が臨界になる」状態からは程遠い。**上位 5 という切り口が、
`clk_pl_1` 側の 5 番目と AXIS 側の 1 番目がたまたま近い所にあるために、
配置が少し動くと入れ替わるだけである。**

**ただし proj007 の書き方は、この入れ替わりで文字どおりには成り立たなくなった。**
上位 N という指標は**順位であって余裕ではない**ので、記録には
「AXIS の最良 slack が +0.766 ns」のように**量**で書くほうが持ちが良い。

| **グリッチ** | **trig 0 / comp 3** ← 未解決 |

配線は ADC 側 4 本が同じ長さ、ADC 側と PPS 側の差 10 cm 以下。
**10 cm ≒ 0.4 ns はビート量子化（6.51 ns）より 1 桁小さい**ので、絶対値の較正定数にも効かない。
ch 間の差にはそもそもケーブルが効かない（4 本が同じ長さなので）。

### 未解決: COMP 経路のグリッチ（trig 0 / comp 3）

`pps_count = 3` に対して `c_glitch = 3`。**PPS 1 発につき COMP がちょうど 1 回余計に遷移している**
勘定になる。グリッチ = ブランキング窓（0.5 s = `BLANK_BEATS`）の中に来たエッジ。

**スタンプは壊れていない。** グリッチは `c_age` をリセットせず、`c_stamp` は `c_accept` のときしか
更新されない。較正が読むのは TRIG のスタンプ（`next_start` の `d["stamp"]`）なので、
**proj008 の測定そのものは COMP が汚れていても成立する。**

**採用されたエッジは本物である。** `COMP − TRIG` が proj007 の 58.6 ns と 0.01 ns で一致しており、
雑音エッジが先に採られているのではない。**余分なエッジは「その後 0.5 秒のどこか」に来ている。**

#### **最初の見立て（結果を知る前に記録）**

**H1（振幅）**: 5 分配で `PPS Clk` のレベルが下がり、LMV7235 のオーバドライブが減って
スイッチが遅くなり、**閾値付近で複数回遷移している**。TRIG がきれいなのは
シュミットトリガのヒステリシスで掃除されるから。proj007 の
「LMV7235 の伝搬遅延はオーバドライブ依存」と同じ軸。

**H2（反射・終端）**: 5 分配で接続点とスタブが増え、**パルスにリンギングが乗って**
閾値を余分に横切っている。100 µs パルスの立ち下がりの跳ね返りなら、
1 発につきちょうど 1 回という観測と合う。

**H1 と H2 は「オシロで `PPS Clk` の波形を見る」1 回で分かれる**（振幅が下がっているのか、
リンギングが乗っているのか）。**レジスタを疑う前に信号を測る** — proj004 で踏んだ順路を繰り返さない。

**なぜ潰すか。** 測定は TRIG で成立するが、(1) 判定 6（持続性）で偽の警報が積み上がる、
(2) `PPS Clk` の入力が際どい状態で走っていること自体が TRIG 側の潜在的な危険である。

#### **【決着】H1 は否定。反射源は 4 分配器で、2 分配器の回り込みで `PPS Clk` を汚していた**

**glitch は `pps_count` と厳密に 1:1** だった（`--watch 120` で `0/8` → `0/123`、
受信数と完全に一致）。起動時の一過性ではなく、**PPS 1 発につき必ず 1 回**。

オシロで `PPS Clk` を見た（RIGOL MSO5354 / 2 V/div / 100 µs/div）。

| | 波形 |
|---|---|
| **10 dB パッド前** | 立ち上がりに **30〜50 µs**。頂部は丸まり**パルス中に垂れ下がる**。長い尾。**100 µs のパルスとして読めない** |
| **10 dB パッド後** | 立ち上がりが速く、平坦部を持ち、立ち下がりも速い。**幅が約 100 µs** で proj007 のオシロ実測と一致 |

**H1（振幅）は否定された。** 減衰器を足す = 振幅を下げる操作で、エッジが**改善した**。
H1 が正しければ逆に悪化していたはずである。**H2（整合・反射）が残る。**
パッドを不整合な界面に入れると反射波はパッドを 2 回通るので、**10 dB のパッドが反射に対して 20 dB 効く。**

**そして反射源が特定できた。パッドを入れたのは ADC 側の 4 分配の手前であって、
`PPS Clk` の経路ではない。** それなのに `PPS Clk` の波形が直った。

```
1PPS ─┬─────────────────────────▶ PPS Clk      ← 触っていないのに直った
      └─(−10 dB パッド)─ 4分配 ─┬▶ ADC_A       ← パッドを入れたのはこちら
                                 ├▶ ADC_B / ADC_C / ADC_D
```

**4 分配器が反射源で、その反射が 2 分配器の有限なアイソレーションを通って
`PPS Clk` 側へ回り込んでいた。**

**触っていない側が直ったことが決定打だった。** もしパッドを `PPS Clk` 側に入れて直っていたら、
「振幅を変えたから」と「整合を変えたから」が分離できず、H1 と H2 の区別がつかなかった。
**対照は狙って置かなくても、変えた場所と直った場所がずれていれば成立する。**

#### 予言（測る前に記録）

**パッドを入れた状態で `comp glitch` は 0 になるはず。** パッド前の形は閾値付近を
1 パルスあたり 3 回以上横切りうる（立ち上がり → 垂れ下がり → 尾の戻り）のに対し、
パッド後は 2 回しか横切らない。**glitch が 1:1 だったこと**は「余分な立ち上がりがちょうど 1 回」で、
この描像と整合する。**外れたら、原因は波形ではない。**

#### **【新しい規約】1PPS の分配に RF 分配器を裸で使わない**

分配器の各枝に**パッドを入れて整合を取る**。1PPS はほぼ DC + 速いエッジで、
RF 分配器の想定する信号ではない。**ADC 側のパッドはレベル合わせのためだけではなく、
整合のためにも要る** — proj008 の測定精度は ADC 側のエッジの速さで決まるので、
`PPS Clk` 側より ADC 側のほうが効く。

**ただし ADC 各枝の中（分配器の出力 ↔ バラン）で往復する反射は、4 分配の手前のパッドでは消えない。**
消したければ各枝の ADC 直前にパッドが要る。**入れるかどうかは `pps_delay.py` の SNR と
エッジ位置の σ を見てから決める**（減衰は SNR を削るので、先回りして入れない）。

### 判定 1 の決着と、判定 2〜4（2026-09-18）

**予言は当たった。** 10 dB パッドを入れた状態で `--watch 60` は **glitch 0/0** のまま。
原因は波形（4 分配器の反射）で確定。判定 2 も **60 秒で残差 0 ビート = +0.0000 ppb**。

#### 判定 2（極性の対照）— **proj006 の 180° を 3 つ目の独立な方法で確認**

| ch | SMA | Tile | ピークの符号 |
|---|---|---|---|
| 0 / 1 | ADC_D / ADC_C | 224 | **＋** |
| 2 / 3 | ADC_B / ADC_A | 226 | **−** |

proj006 は CW トーンの位相で、proj008 は **PPS のエッジの符号**で見ている。
**タイルできれいに分かれた。**

ADC 側の SNR は **48〜53 dB**、ピーク −12.6〜−12.9 dBFS。飽和なし・SNR 不足なし。
**各枝へのパッド追加は不要**（減衰は SNR を削るので、必要がなければ入れない）。

#### 判定 3（タイル内）— **達成。proj006 を別の方法で再現した**

| | 差 | 実行内 σ |
|---|---|---|
| Tile 224 | ADC_C − ADC_D = **−0.011 ± 0.009 サンプル**（−0.009 ns）| 0.024 ns |
| Tile 226 | ADC_A − ADC_B = **+0.000 ± 0.011 サンプル**（+0.000 ns）| 0.029 ns |

proj006 の予言（σ 0.018 /「0.02 サンプル以内」）と整合。
**proj006 は CW トーンの位相、proj008 は PPS のエッジ。まったく違う方法で同じ量を測って、
9 ps で一致した。** 両方を信用してよい。

**→ 同じタイルの ch は 1 本の PPS で較正できる。**

#### 判定 4（タイル間）— 測れたが、**この 1 回では proj006 と比べられない**

```
Tile 226 − Tile 224 = +3.312 ± 0.006 サンプル (+2.696 ns)   実行内 σ 0.016 ns
```

| ch | 整数ビート | 小数 [sample] |
|---|---|---|
| 0 / 1（T224）| 32 | 6.14 / 6.13 |
| 2 / 3（T226）| 33 | 1.45 / 1.45 |

#### **【訂正】平均オフセットと RMS を比べていた**

`pps_delay.py` は当初「proj006 の予言（1〜1.5 サンプル）より大きい」と印字した。
**この比較は成立していない。**

proj006 がタイル間について測ったのは **CW の位相を巻き戻した「起動ごとのばらつき」**である。

| | 10.0125 MHz | 13.0125 MHz |
|---|---|---|
| タイル間の**幅** | 2.64 サンプル | 5.30 サンプル |
| 同 **標準偏差** | 0.93 | 1.50 |

「1〜1.5 サンプル RMS」は**起動ごとの σ** であって、**あるエポックでの平均オフセットではない。**
proj008 が出したのは後者なので、**種類の違う量を比べていた。**
しかも **+3.312 サンプルは proj006 の幅 2.64〜5.30 の中に入っている** — 矛盾は最初から無かった。

**直した。** 単一エポックの判定 4 では当たり外れを言わず、平均と精度だけを報告する。
proj006 と比べられるのは **エポックをまたいだ平均の σ** だけなので、比較はそちらへ移した。

**教訓**: **予言を定数に埋め込むときは、その定数が「平均」なのか「ばらつき」なのかを
一緒に書く。** 元の実装は `PRED_CROSS_TILE_SAMPLES = 1.5  # タイル間は 1〜1.5 サンプル RMS` と
コメントに RMS と書いておきながら、`abs(mu) <= 1.5` という平均との比較に使っていた。
**コメントが正しくてコードが間違っている形は、読んでも気づけない。**
定数名を `PRED_CROSS_TILE_RMS` にして、使う場所を σ の比較だけに限った。

### 判定 5（`--epochs 5`）— **測定方法の非対称性を測っていた**

`--epochs 5 --trials 5` を実行した。ツールは「タイル間の差はエポックごとに変わる
（σ 12.423 サンプル / 幅 31.808 サンプル）→ 構成 B は科学 2ch」と印字した。
**この数字は装置の性質ではない。**

| epoch | Tile 224 [sa] | N | Tile 226 [sa] | N |
|---|---|---|---|---|
| 1 | 265.17 | 33 | 266.61 | 33 |
| 2 | **297.40** | **37** | 267.01 | 33 |
| 3 | **289.00** | **36** | 266.50 | 33 |
| 4 | **289.26** | **36** | 263.18 | 32 |
| 5 | **281.04** | **35** | 264.97 | 33 |
| **幅** | **32.2 サンプル（4 ビート）** | | **3.8 サンプル（1 ビート未満）** | |

**タイルごとに動き方がまったく違う。**

- **Tile 224 は 32 サンプル（4 ビート）動く。** しかも**小数部はほぼ一定**
  （1.17 / 1.40 / 1.00 / 1.26 / 1.04）で、**整数ビート N だけが跳んでいる**。
  proj007 の「エポック間で動くのは整数ビートだけ」と同じ形
- **Tile 226 は 3.8 サンプル（1 ビート未満）しか動かない**

#### **【踏んだ穴】エポックを作る操作が非対称だった**

`--epochs` は `--src-tile 2`（= MMCM の源である **Tile 226**）だけを
`ShutDown()` / `StartUp()` する。`start_tiles()` は既定で `restart=False` なので、
**Tile 224 は最初から最後まで一度も触られていない。**

**動いたのは、止めなかったほうのタイルである。**

AXIS クロック（ビートカウンタのクロック）は Tile 226 の `clk_adc2` から MMCM で作られる。
Tile 226 を止めて起動し直すと MMCM が張り直され、**AXIS クロックの位相が動く**。

- Tile 226 は自分のデータパスと AXIS クロックが同じ源なので、ずれは 1 ビート未満に収まる
- Tile 224 はデータパスの位相が据え置かれたまま AXIS クロックだけが動くので、
  **どのビートに載るかが変わる** → 整数ビートで跳ぶ

**したがって「タイル間差の σ 12.4 サンプル」は、片方のタイルだけを触ったことの
反映がほぼそのまま出ている。** 結論の**向き**（タイルごとに PPS が要る）は変わらないかもしれないが、
**根拠と量が測定方法の副産物**なので、このままでは構成 B の設計判断に使えない。

#### 直したこと

- **`--epoch-mode` を足した。** `src`（従来）/ `both`（両タイルを止めて起動し直す・**既定**）/
  `overlay`（Overlay を焼き直す。**実運用のエポック変化に最も近い**）
- **タイルごとのエポック間変動を別々に出すようにした。**
  タイル間の**差**だけを見ていると「片方だけが動いている」ことに気づけない。
  片方がもう片方の 3 倍以上動いていたら、**測定方法を疑えと自分で言う**

**教訓**: **対照を置く場所を間違えた。** proj006 / proj007 では「条件を 1 つだけ変える」を
守っていたが、ここでは**変えた 1 つの条件がタイルについて非対称だった**。
「1 つだけ変えた」は、**その 1 つがすべての被測定対象に対等に効くとは限らない。**

#### **【踏んだ穴】RFDC タイルの起動には順序の依存がある**

`--epoch-mode both` の初回実行が落ちた。

```
RuntimeError: Function XRFdc_StartUp call failed
 ADC 0 timed out at state 14 in XRFdc_WaitForRestartClr
```

`build.tcl` は**全タイルの `m<n>_axis_aclk` を Clocking Wizard の出力**に繋いでおり、
その Wizard の入力は **Tile 226 の `clk_adc2`** である。両タイルを止めると
`clk_adc2` が消えて MMCM が外れ、**Tile 224 は AXIS クロックが無い状態**になる。
その状態で `StartUp()` を呼んでもタイルの状態機械は進まない。

**止めるときは源を最後に、起動するときは源を最初に。** 源を起動して `locked` を待ってから
残りを起動するよう直した。失敗したときは AXIS クロックの依存を名指しで説明して止まる。
`VERSIONS.md` にも書いた（**1 タイルだけを扱っている限り表に出ない**性質なので）。

**順序を直しても成立しなかった。** 源（Tile 226）を先に起動すると、今度は源自身が
`ADC 2 timed out at **state 3**`（クロック検出）で止まる。

| 起動順 | エラー |
|---|---|
| 0 → 2 | `state 14`（AXIS クロックが無い）|
| 2 → 0（源が先）| `state 3`（クロック検出で止まる）|

**源を単独で止めて起動する `src` は 5 エポック通る**ので、
**「もう片方も止めた」こと自体**が効いている。**順序の問題ではなかった。**

**深追いしない。** `--epoch-mode overlay` は `ShutDown()` を一切使わず、
ビットストリームを焼き直して全タイルを同時に立ち上げ直す。
**同じ目的を果たし、しかも実運用のエポック変化に近い。** 既定を `overlay` にした。
`both` は残してあるが、失敗したときに `overlay` を使えと言う。

**この失敗自体が、前節の非対称性の裏付けになっている。**
「Tile 224 の AXIS クロックが Tile 226 に依存している」ことが、
エラーという形で独立に確認された。**`--epoch-mode src` で Tile 224 だけが動いたのは、
まさにこの依存があるからである。**
