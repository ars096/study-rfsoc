# proj006 — 4ch 同時取得とタイル間のずれの素性

日付: 2026-09-17
状態: 進行中（**ビルド成功。実機での取得はこれから**）

## 目的

ADC_A / B / C / D の 4 本を **同じビートで** 取得し、SMA のラベルとタイル / スライスの
対応を実測で確定する。そのうえで、**タイル間のサンプルずれが起動ごとに変わるかどうか**
を測る。

proj006 の成果物はビットストリームではない。**「4ch が同時に取れる」ことと、
「タイル間のずれが較正できる量なのかどうか」の答え**である。

## なぜこれが自明でないか

ADC_A / B は Tile 226、ADC_C / D は Tile 224 に載る。**この 4 本は 1 個の LMX2594 から
491.52 MHz をもらう**（RefMan: ADC 用と DAC 用に LMX2594 が 1 個ずつ）。したがって
サンプリングクロックは同一で、位相も固定である。

**にもかかわらず、タイル間でサンプルの番号が揃う保証はない。**

RFDC はコンバータのクロック領域と AXI4-Stream の領域の間に内部 FIFO を持つ。この FIFO の
読み出しが始まる位相はタイルの起動シーケンスで決まり、**タイルごとに、そして起動ごとに
変わりうる**。MTS（Multi-Tile Synchronization）が揃えているのは、突き詰めればこの
FIFO のポインタである。

分光計としては、ずれが「毎回同じ」なら定数として引けばよく、MTS は要らない。
「毎回違う」なら MTS か、起動ごとの較正が要る。**どちらなのかを先に測る。**
これが proj006 の本題で、4ch 取得はそのための道具である。

proj004 が「外部基準が効いている」と言い切れる状態を作ったのと同じ構図で、
proj006 は「タイル間のずれの素性」を言い切れる状態を作る。

## 同期の 3 層のどこにいるか

2026-09-17 の検討で、この開発での「同期」を 3 層に分けた。

| 層 | 揃えるもの | 手段 | 状態 |
|---|---|---|---|
| ① 周波数 | fs の確度とボード間コヒーレンス | 外部 10 MHz → CLK_IN | **proj004 で完了**（−0.015 ppm）|
| ② サンプル位相 | タイル間 / ボード間のサンプル境界 | SYSREF / MTS | **proj006 はここを「測る」。揃えるとは言っていない** |
| ③ 絶対時刻 | エポック、積分窓の開始 | 1PPS | proj007 |

45m 鏡では 1PPS が機器に分配されている。SAM45 の代替＝自己相関スペクトルであれば、
ボード間に必要なのは①と③だけで、②のボード間コヒーレンスは要らない
（2026-09-17 に確認）。**②はボード内（タイル間）の話としてだけ残る。**

## 設計

### 4ch を 1 本のストリームに束ねる

```
 rfdc.m00_axis (128b) ┐
 rfdc.m02_axis (128b) ├─▶ axis_combiner ─(512b)─▶ capture_gate ─▶ axis_data_fifo ─▶ axi_dma ─▶ HP0
 rfdc.m20_axis (128b) │       (4→1)                 (DATA_W=512)      (非同期・64B語)
 rfdc.m22_axis (128b) ┘
```

束ねる理由は 4 つある。

1. **同時性が構造的に保証される。** 1 本のストリームの同じビートに 4ch が乗るので、
   「4 つのゲートを同時に起動する」という問題そのものが消える
2. `capture_gate` は `DATA_W` をパラメータで持っている。**512 にするだけで改修は要らない**
3. FIFO も DMA も 1 個で済む
4. PYNQ 側は 1 回の転送で 4ch 分を受け取り、`reshape` で分けられる

デシメーション 1 / Real では RFDC のストリームは常時 valid である。`axis_combiner` は
**4 本すべてが valid のときだけ**出力を出すので、どれかのタイルが起動していなければ
1 ビートも出ない。**気づける失敗の仕方**になっている。

チャネルの並び（S00 が最下位バイト）は、実機で 1 本ずつ信号を入れて確定させる。
**推定で表を書かないこと**（proj003 で「SMA のラベルとスライス番号の並びが逆」を踏んでいる）。

### AXIS クロックは MMCM 1 個を 2 タイルで共有する

RFDC の `clk_adc0` と `clk_adc2` は、どちらも fs/16 = 76.8 MHz を出す。
このうち **`clk_adc2` だけを Clocking Wizard に入れて 153.6 MHz を作り、
`m0_axis_aclk` と `m2_axis_aclk` の両方に配る。**

2 個置くと MMCM 2 個分の位相不定を持ち込むことになる。同じ 491.52 MHz 起源で
周波数は同一なので、1 個で足りる。proj005 との差分も小さくなる。

**「各タイルが自前のクロック入力を持つ」は 2026-09-17 のビルドで確認した。**
RFDC IP のインタフェース一覧に `adc0_clk` と `adc2_clk` が別々に出る。
したがって `Clock_Dist 0`（クロック転送を使わない）で正しい。
アナログ入力も `vin0_01` / `vin0_23` / `vin2_01` / `vin2_23` の 4 本で、
スライスの対ごとに分かれている。

### 取得長は FIFO の深さで上限する

**ここが proj005 からの一番大きな方針転換である。**

| | 値 |
|---|---|
| 流入 | 512 bit × 153.6 MHz = **9.8304 GB/s** |
| 流出（HP0 は 128 bit 止まり） | 128 bit × 175 MHz = **2.8 GB/s** |

4ch フルレートの連続ストリームは成立しない。HP を 4 本に分けても、PS の DDR4 を
Linux と共用している以上、9.83 GB/s を持続させるのは無理がある。

そこで **`n_beats ≤ FIFO 深さ` を守ることで、FIFO が溢れないことを原理的に保証する。**
DMA が間に合うかどうかを見積もる必要がなくなる。

| | 値 |
|---|---|
| FIFO | 512 bit × 8192 語 = **512 KiB**（BRAM36 換算 128 個 / ZU48DR は 1080 個）|
| 最大取得長 | 8192 ビート = **65536 サンプル/ch** = 53.3 µs |

65536 サンプルは proj003 / proj005 と同じで、CW の解析には足りている。
伸ばしたくなったら `FIFO_MEMORY_TYPE` を `ultra` にして URAM（80 個 × 288 Kb）へ
逃がす道がある。**その必要が出るのは分光計本体ではなく測定器としての用途だけである。**

### 外部 10 MHz

`pynq/extref.py` を proj004 / proj005 からそのまま持ち込む。**測定は必ず外部基準で行う。**
タイル間のずれを測るときに fs がずれていると、位相の読みが時間とともに回る。

## 決めたこと

- **決定**: 4ch を 512 bit の 1 本に束ねる
  **理由**: 上記のとおり同時性が構造的に保証され、`capture_gate` の改修が要らない
  **見送った案**: `capture_gate` を 4 レーン並べ、同じ `arm` を配る案。
  各インスタンスが**独立の 3 段同期器**を持つため、メタステーブルの解決が個体ごとに
  1 クロック違いうる。「同時に起動したはず」が「ときどき 8 サンプルずれる」に化け、
  しかも**測ろうとしている量と区別がつかない**。同期器を 1 個に括り出す改修でも
  直せるが、束ねれば問題自体が消える

- **決定**: 連続ストリームを諦め、取得長を FIFO 深さ以下に制限する
  **理由**: 4ch フルレートは 9.83 GB/s で、PS 側の帯域が足りない。そして
  **分光計本体では生サンプルを DDR へ流さない** — PL 内で FFT と積分をする。
  生データ全量の DMA は proj003 が作った「測定器」の都合であって、最終形ではない
  **見送った案**: HP を 4 本使って 4ch 連続ストリームを維持する案
  **付随**: `build.tcl` の帯域チェック（余裕 10% 未満で停止）は意味を失う。
  **消さずに「FIFO 深さ × 語幅 ≥ 取得長」の検査に差し替える。**
  検査を消すと、次に誰かが取得長を伸ばしたときに黙って壊れる

- **決定**: **MTS は proj006 の成功条件にしない**
  **理由**: 4 つある。
  (1) 自己相関スペクトルではタイル間・ボード間のサンプル位相コヒーレンスは要らない
  （2026-09-17 に確認）。MTS は「あると綺麗」であって必須ではない
  (2) AMD の参照デザイン `Xilinx/RFSoC-MTS` は 4x2 向けに **LMK / LMX を 500 MHz 系へ
  張り替える**構成である。これを採ると 491.52 / 1228.8 を捨てることになり、
  **proj003〜005 の fs と proj004 の外部基準がまるごと無効になる**
  (3) その 500 MHz 構成で **4x2 の LMK の PLL1 / PLL2 がロックしない**という
  未解決の issue がある（`Xilinx/RFSoC-MTS` issue #3）
  (4) MTS は PL 側で捕まえた SYSREF（`user_sysref_adc`）を要求するが、
  **RFSoC 4x2 の RefMan にも BSP の board file にも PL SYSREF のピンが出てこない。**
  存在するかどうかが未確認
  **代わりに置くもの**: 「タイル間のずれが起動ごとに変わるか」の実測。
  変わらなければ MTS は不要だと言える。変わるなら、そこで初めて別 proj で取りに行く

- **決定**: Clocking Wizard は 1 個。`clk_adc2` から作った 153.6 MHz を両タイルへ配る
  **理由**: 上記
  **見送った案**: タイルごとに Clocking Wizard を置く案

- **決定**: proj005 のディレクトリをコピーして作る（`template/` ではなく）
  **理由**: 差分が「4ch 化」だけになり、何を変えたのかが git の diff にそのまま出る。
  リポジトリの方針（各 proj は自己完結・再現性 > DRY）は保たれている

- **決定**: 一番きつい経路のクロック対を、**WNS が正でも必ず出す**
  **理由**: proj005 の診断は「WNS < 0 のときだけ違反経路を出す」作りだった。
  これでは **「宣言し忘れた乗り換えが、たまたま間に合っていただけ」を見逃す。**
  通ったかどうかは合否であって、設計が理解できているかとは別である。
  setup / hold それぞれ上位 5 本を、起点と終点のクロック付きで出す。
  **クロック対が違えば「← 乗り換え」と印を付ける**
  **見送った案**: WNS の値だけを見て次に進む案

- **決定**: **宣言していないクロックに経路が無いことを、数えて確かめる**
  **理由**: timing.xdc は `clk_pl_0` / `clk_pl_1` / `RFADC2_CLK` の 3 群しか
  宣言していない。proj006 は `clk_adc0` を繋いでいないので `RFADC0_CLK` には
  経路が無い **はず** — だがこれは推定である。`get_timing_paths -from/-to` で
  数えれば事実になる。proj004 の「CLK_IN がどの CLKin かは配線図ではなく実測で決める」
  と同じ扱いをクロック制約にも適用する
  **見送った案**: 「無いはずだから書かない」で済ませる案。
  なお **timing.xdc に `RFADC0_CLK` を書き足す方向は採らない** —
  `get_clocks` が空を返したときに `set_clock_groups` が落ちるので、
  「あるかもしれないもの」を XDC に書くのは避ける（XDC では if が使えない）

- **決定**: 乗り換えの分類は **`report_cdc` を正とする**。自作の経路数えは補助に降ろす
  **理由**: 上記の偽陽性。`get_timing_paths` は「経路の有無」しか答えず、
  **「解析されているか」には答えない。**`report_cdc` は乗り換えを
  Critical / Warning / Info に分類する専用コマンドで、IP が自前の制約で
  処理済みのものも正しく扱う。自作の数えは残すが、**slack を持つ経路だけ**に絞り、
  **対照（宣言済みの `RFADC2_CLK`）も必ず並べる**
  **見送った案**: `RFADC0_CLK` 等を timing.xdc の `set_clock_groups` に足す案。
  **存在しない問題に対する対処**になるうえ、`get_clocks` が空を返したときに
  制約が落ちる危険を持ち込むだけだった
  **結果**: `report_cdc` の `Exception` 列が決着をつけた。同じ経路が
  RFDC IP の `False Path` とこちらの `Asynch Clock Groups` で二重に処理されていた

- **決定**: `capture_gate` の同期器 3 本に **`ASYNC_REG = "TRUE"` を足す**
  **理由**: `report_cdc` の CDC-2。**proj005 から引き継いでいた漏れ。**
  無くても動くし、タイミングも閉じるし、波形にも出ない。**MTBF だけが静かに落ちる。**
  この種の欠陥は、動作確認では絶対に見つからない
  **付随**: proj005 の `capture_gate.v` とはここで差分が出る。
  リポジトリの方針（各 proj は自己完結・再現性 > DRY）どおり、proj005 には遡及しない

- **決定**: `n_beats` の乗り換え（CDC-1 が 26 件）は **直さない**
  **理由**: ソフトが「値を書く → 同じ値に arm だけ足して書く」順で叩くので、
  arm の遷移時に `n_beats` のビットは**遷移しない**。乗り換えているのは
  `arm` の 1 bit だけで、それは 3 段の同期器を通る。
  **Vivado はソフト側の手順を見られないので、この構造は必ず Critical になる**
  **見送った案**: `set_max_delay -datapath_only` を張って経路長を縛る案。
  正攻法ではあるが、**proj006 の判定条件は「4ch が同時に取れること」**であって
  RTL の堅牢化ではない。タイミング収束をいじる変更を今入れると、
  失敗したときに何が原因か言えなくなる。**分光計本体を組むときに改めて向き合う**

## 成功の判定

1. 4ch すべてで CW が取れ、**周波数が 4 本とも一致する**
2. **SMA ラベル ↔ (tile, slice) の対応表が 4 本とも実測で埋まる**
   （`VERSIONS.md` の「推定」「未確認」を消す）
3. 同じ信号を 4 分配して入れたとき、**ch 間のサンプルずれが Overlay の読み直し N 回で
   毎回同じか、毎回違うかが言える**
4. WNS ≥ 0

**3 は「揃っていること」ではなく「どちらなのかが言えること」を判定にしている。**
揃っていなくても proj006 は成功でよい。揃っているかどうかは、この先の設計
（較正で足りるか、MTS が要るか）を分ける事実であって、proj006 の出来不出来ではない。

## 着手条件

- **4 分配器（パワースプリッタ、〜1 GHz 級）とケーブル 4 本。**
  ずれを測るには同じ信号を 4ch に入れる必要がある。**ケーブル長は揃える**
  （1 ns ≒ 20 cm ≒ 1.2 サンプル。長さの差がそのままずれに化ける）
- **分配器が無い場合の逃げ道**: 2 分配で **ADC_B（Tile 226）と ADC_D（Tile 224）**の
  2 本に入れる。タイル間という問いには 2ch で答えが出る。同一タイル内のスライス間は
  構造上揃っているはずなので後回しでよい
- **トーンの選び方**: ずれは CW の位相差で測る。**1 周期がずれの範囲より長いトーンを選ぶ。**
  10.0125 MHz なら 1 周期 = 122.7 サンプルで ±61 サンプルまで一意に決まる。
  念のため 2 つの周波数で測って整合を取ること
- 経路の減衰量を記録する（proj005 で決めた規約）

## 結果

### ビルド（2026-09-17）

| | 値 | 比較 |
|---|---|---|
| WNS | **+0.300 ns** | proj005 は +1.014 ns。**0.7 ns 減った** |
| WHS | **+0.004 ns** | 閉じてはいるが余裕は 4 ps |
| BRAM | **RAMB36 123 個 / 1080**（11.4%）| FIFO 512 KiB ぶんの見積り 128 個とほぼ一致 |
| URAM | 0 / 80 | 取得長を伸ばすときの逃げ道は残っている |
| CRITICAL WARNING | **なし** | |
| 非同期宣言 | `clock_interaction.rpt` に 7 箇所 | 効いている |

`make sim`（`capture_gate` のテストベンチ）は ALL PASS。

**WNS が 0.7 ns 減っている理由は、この時点では言えなかった。** 語幅が 128 → 512 bit に
なって設計が重くなっただけかもしれないし、宣言し忘れた乗り換えが解析に残っていて、
たまたま間に合っているだけかもしれない。**通ったかどうかだけ見ていると後者を見逃す。**

そこで build.tcl に診断を足して測り直した（下の「決めたこと」）。**答えは前者。**

```
---- 一番きつい経路 上位 5  setup（周期） ----
  slack 0.300 / 0.326 / 0.424 / 0.456 / 0.475   すべて clk_pl_1 → clk_pl_1
---- 一番きつい経路 上位 5  hold（保持） ----
  slack 0.004 / 0.008 / 0.012   clk_pl_0 → clk_pl_0
  slack 0.011 / 0.012           clk_pl_1 → clk_pl_1
```

**上位はすべて同一ドメイン内で、乗り換えは 1 本も入っていない。**
したがって 0.7 ns の減少は制約の漏れではなく、**512 bit のデータ経路を
pl_clk1（175 MHz）で捌いていることによる**。DMA と SmartConnect が
512 → 128 bit の変換を抱えている側である。**設計が重くなっただけ**と言い切ってよい。

hold の 4 ps は router が詰めた結果（route の途中で WHS = −0.040 → 最終 +0.004）。
**hold は周波数を下げても直らない**ので、将来悪化したときの手は配置配線であって
制約ではない。閉じてはいるので proj006 はこのまま進める。

### 宣言していないクロックの経路 — **偽陽性だった**

1 回目の診断で、`RFADC0/1/3_CLK` と `RFDAC0..3_CLK` に「起点 8 本」が出た。
制約漏れを疑ったが、**違った。**

```
  RFADC0_CLK  → clk_pl_0  8 本  最悪 slack (空)   終点: rfdc/inst/IP2Bus_Data_reg[9]/D
  RFADC2_CLK  → clk_pl_0  8 本  最悪 slack (空)   ← **timing.xdc で宣言済みなのに同じ**
  RFDAC0_CLK  → clk_pl_0  8 本  最悪 slack (空)
  （以下同様）
```

**`get_timing_paths -from <clock>` は slack を持たない経路 — つまり解析対象外の
経路 — も返す。** 終点はいずれも `rfdc/inst/IP2Bus_Data_reg[*]/D` で、RFDC IP の
内部でタイルのステータスが AXI4-Lite の読み出しレジスタへ渡る経路である。
**IP が自前の制約で処理済み**だから slack が空になっていた。

**対照（宣言済みの `RFADC2_CLK`）を並べていたから、偽陽性だと分かった。**
片方しか見ない診断は、診断自体が嘘をつく。proj004 で「効果で検証する」と決めたのと
同じ話が、診断コードにも当てはまる。

裏付けは 3 つ揃っている。

1. 宣言済みの `RFADC2_CLK` が未宣言のものと**同じ出力**を返した
2. setup / hold の上位 5 本に 1 本も入っていない
3. `clock_interaction.rpt` に asynchronous が 7 箇所あり、宣言は効いている

**timing.xdc は変更しない。** 代わりに診断を 2 段構えにした（下記）。

### report_cdc が出した答え（2026-09-17）

```
CDC-1   Critical     26  1-bit unknown CDC circuitry
CDC-2   Warning       3  1-bit synchronized with missing ASYNC_REG property
CDC-3   Info         15  1-bit synchronized with ASYNC_REG property
CDC-11  Critical      2  Fan-out from launch flop to destination clock
CDC-15  Warning      89  Clock enable controlled CDC structure detected
```

**まず、上の偽陽性の件に決着がついた。** `Exception` の列がそれを言っている。

| 送り元 | Exception |
|---|---|
| `RFADC0/1/3_CLK`, `RFDAC0..3_CLK` → `clk_pl_0` | **`False Path`** — RFDC IP が自前で張っている |
| `RFADC2_CLK` → `clk_pl_0` | `Asynch Clock Groups` — こちらの timing.xdc |

**同じ経路が、IP の制約とこちらの制約という別々の手段で、どちらも処理されていた。**
だから slack が空だった。timing.xdc に足す必要はやはり無い。

残りを、**IP の中の話**と**こちらの RTL の話**に分ける。

#### こちらの RTL（`capture_gate`）— CDC-2 が 3 件。**これは本物**

```
gpio_Data_Out_reg[0]/C  → capture_gate_0/inst/arm_sync_reg[0]/D
capture_gate_0/inst/running_reg/C → capture_gate_0/inst/busy_sync_reg[0]/D
capture_gate_0/inst/done_r_reg/C  → capture_gate_0/inst/done_sync_reg[0]/D
```

**同期器の 3 本すべてに `ASYNC_REG` が付いていなかった。**
これが無いと、同期器の段が離れた場所に置かれうる。段の間の配線が延びたぶんだけ
準安定の収束に使える時間が減り、MTBF が落ちる。**機能は変わらないので気づけない。**
`report_cdc` が唯一の検出手段だった。

**proj005 から引き継いでいた漏れである。** `capture_gate.v` に
`(* ASYNC_REG = "TRUE" *)` を 3 箇所足した。

#### こちらの RTL — CDC-1 が 26 件。**既知・許容**

```
gpio_Data_Out_reg[9]/C → capture_gate_0/inst/remain_reg[*]/CE, done_r_reg/D, running_reg/D
```

`n_beats`（24 bit）が同期器を通らずに `remain` のロードと状態遷移の条件
（`n_beats != 0`）に入っている、という指摘。**これは proj005 で意図的にそうした箇所**で、
`capture_gate.v` と `src/timing.xdc` の両方に理由を書いてある。

根拠は取得側の手順にある。`pynq/adc_capture.py` は

1. `n_beats` を書く（arm = 0）
2. DMA を張る
3. **同じ値の `n_beats` に arm ビットだけ足して**書く

の順で叩く。3 の書き込みで `n_beats` のビットは**値が変わらないので遷移しない**。
乗り換えているのは実質 `arm` の 1 bit だけで、それは 3 段の同期器を通る。
`arm_rise` が立つ頃には `n_beats` は数 µs 以上静定している。

**Vivado はソフト側の手順を見られないので、この構造は必ず Critical になる。**
これは「データ＋ハンドシェイク」の宿命であって、直すべき欠陥ではない。

#### IP の中 — CDC-11 が 2 件、CDC-15 の大半

```
rst_adc/.../FDRE_PER_N/C → rfdc/inst/cdc_adc0_clk_valid_i/syncstages_ff_reg[0]/D
                         → rfdc/inst/cdc_adc2_clk_valid_i/syncstages_ff_reg[0]/D
```

`rst_adc` のリセットが RFDC IP の内部同期器に入っており、その送り元フロップが
他にも扇を広げている、という指摘。**リセットは MMCM がロックした時点で一度
解除されたきり静定する**ので、準安定の窓は起動時の一度だけで、その一度も
IP 側の同期器が受けている。proj006 では触らない。

CDC-15 の 89 件はほぼ全部が `INTERNAL_FBRC_MUX → IP2Bus_Data_reg[*]` で、
上の表のとおり例外が張られている。

### 確定値（`ASYNC_REG` を足したあと）

| | 1 回目 | **確定** |
|---|---|---|
| WNS | +0.300 ns | **+0.588 ns** |
| WHS | +0.004 ns | **+0.015 ns** |
| CDC-2（ASYNC_REG なし）| 3 | **0** |
| CDC-3（ASYNC_REG あり）| 15 | **18** |
| CDC-1 / CDC-11（Critical）| 26 / 2 | 26 / 2（**既知・許容**）|

**CDC-2 が 3 減り、CDC-3 が 3 増えた。** 同期器は「属性なし」から「属性あり」へ
移動しただけで合計は変わらない。3 本とも属性が乗ったことの確認になっている。

**タイミングの改善を `ASYNC_REG` の効果と読んではいけない。**
臨界経路は `clk_pl_1 → clk_pl_1` の 512 bit データ経路で、同期器とは無関係である。
ネットリストが変わったことによる配置配線のばらつき（run 間の揺らぎ）と見るのが妥当。
WHS の方は同期器が同じスライスに寄った効果が入っていてもおかしくないが、
**切り分けはできていない。良くなったことは事実として残し、原因は断定しない。**

proj006 のタイミングと CDC はここで打ち止め。**実機の取得へ進む。**

```
  RFADC0_CLK                      13.021 ns  ( 76.799 MHz)   ← clk_adc0。**未接続**
  RFADC2_CLK                      13.021 ns  ( 76.799 MHz)   ← Clocking Wizard の入力
  clk_out1_system_clk_wiz_adc_0    6.510 ns  (153.610 MHz)   ← AXIS
  clk_pl_0                        10.000 ns  (100.000 MHz)
```

`clk_adc0` をどこにも繋いでいないのでファブリックの経路は無いはずだが、
**これも次のビルドで数えて確かめる。**

## 再現手順

### ビルド（Vivado サーバ）

```bash
make            # 合成〜ビットストリーム生成（build/proj006.bit と .hwh）
make sim        # capture_gate のテストベンチ。Vivado もライセンスも要らない
make timing-check   # 速度グレード -1 で閉じるか（build-1-e/ に出る）
```

### 実機（PYNQ v3.1.1）

**`make prog`（JTAG 書き込み）は使わない。** proj003 以降は PYNQ の `Overlay()` で
ロードする。理由は 2 つある。

1. **PYNQ は `.hwh` を読んでドライバを生やす。** `ol.rfdc` / `ol.dma_adc` /
   `ol.gpio_capture` はこれが無いと現れない。JTAG は `.bit` しか送らないので、
   PL に何が入っているかを PYNQ 側が知らないままになる
2. **`tile_offset.py --mode overlay` は「Overlay を読み直すとタイルが起動し直す」
   ことに依存している**（proj003 で確認）。JTAG で焼いた状態から始めると、
   測ろうとしている起動シーケンスそのものが変わる

```bash
scp build/proj006.bit build/proj006.hwh pynq/*.py xilinx@<board>:~/proj006/
ssh xilinx@<board>
cd ~/proj006

sudo -E $(which python3) adc_capture.py --probe                     # まず構成を見る
sudo -E $(which python3) slice_map.py   --tone 100.0125 --clkin 0   # SMA ↔ ch の対応
sudo -E $(which python3) tile_offset.py --tone 10.0125  --clkin 0 --trials 10
```

**`--probe` で Tile 224 と Tile 226 の両方が `PLLLockStatus = 2` になっていること。**
片方でも落ちていると `axis_combiner` が 1 ビートも出さず、
「データが全く来ない」という症状になる（意図した失敗の仕方）。

`make prog` と `make id` は残してある。**ケーブルとボードの生存確認**には使える
（`make id` は合成ライセンスが要らない）。
